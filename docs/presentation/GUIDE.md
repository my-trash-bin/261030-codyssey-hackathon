# 해커톤 발표 가이드

제품 의도/요구사항/구현 사실의 정본은 [README의 외부 문서 안내](README.md)를 따른다.
이 문서는 말하는 순서와 근거 준비를 위한 발표용 가이드다. B2B 솔루션 포장은
[결정 PRES-DEC-01](../decisions.md)에 근거한다. 심사위원의 전문 수준을 단정하지 않고, 서로
다른 배경에서도 문제/기술/사업성의 연결을 빠르게 이해할 수 있게 기업 솔루션 언어로 감싼다.

## 심사 배점과 준비 우선순위

주최 측 배점표의 문구와 점수를 발표 준비 기준으로 사용한다. 1차 서면 심사는 아래 다섯 항목을
각 20점으로 평가한다.

| 평가 항목 | 세부 내용 | 배점 | 문서/근거 준비 |
| --- | --- | ---: | --- |
| 기획의 구체성 | 문제 정의의 명확성, 목표 사용자, 실행/확장 계획의 구체성 | 20 | 문제/사용자/실행 범위/후속 확장을 같은 흐름으로 설명 |
| 기획의 창의성 | 문제 정의의 독창성, AI 기술 적용의 창의성 | 20 | 단순 가림이 아니라 사람이 공개 범위를 정하고 새 공유본을 만드는 차별점 제시 |
| 기술 완성도 | 모델, 알고리즘, 코드 구현의 완성도. 단순 호출이 아닌 직접 개발은 높은 평가 | 20 | 직접 개발 범위와 외부 모델 호출, 현행 구현과 계획을 구분 |
| 성과 및 실용 가능성 | 결과물의 실제 적용 가능성, 문제 해결의 실효성 | 20 | 재현 가능한 데모와 같은 조건의 비교 실험으로 효용을 입증 |
| 팀 구성 및 협업 체계 | 역할 분담의 명확성, 협업 구조와 산출물 간의 일관성 | 20 | 역할별 산출물과 통합 지점을 실제 저장소 결과에 연결 |

2차 대면 심사는 아래 네 항목을 각 25점으로 평가한다.

| 평가 항목 | 세부 내용 | 배점 | 발표 대응 |
| --- | --- | ---: | --- |
| 아이디어 전달력 및 문제 해결력 | 아이디어의 논리성/명확성, 문제 해결 접근 방식의 설득력 | 25 | 문제/사용자/해결 흐름을 먼저 연결하고 선택 이유를 설명 |
| 기술 구현력 및 라이브 시연 완성도 | 구현 결과물의 완성도/기술 수준, 직접 개발 범위, 현장 시연의 정확성/안정성 | 25 | 실제 앱/fixture/녹화 재생을 구분하고 검증된 경로만 라이브로 시연 |
| 적용 가능성 및 확장성 | 실제 활용 가능성/발전 가능성, 질의응답으로 확인된 확장 잠재력 | 25 | 현재 적용 범위와 확장 가설을 분리하고 근거/전제/한계를 답변에 포함 |
| 발표 구성 및 팀워크 | 발표 구성의 명료성, 시간 배분, 역할 수행, 팀원 간 협업과 태도 | 25 | 구간별 담당자/전환 신호/백업 역할을 정하고 리허설에서 시간을 기록 |

배점이 동일하므로 한 항목을 과도하게 강조해 다른 항목의 근거를 빼지 않는다. 특히 기술 구현과
라이브 시연은 직접 개발 범위를 분명히 보여 주되, 현재 코드에 없는 기능을 완료로 설명하지 않는다.

## 7분 발표와 질의응답 운영

발표 7분은 **라이브 시연 3분 이상**과 **설명 4분 이내**로 구성한다. 질의응답 5분은 발표 시간과
별도로 진행한다. 아래 시간표는 리허설 기준이며, 라이브 시연 시간을 줄이는 방향으로 조정하지 않는다.

| 시간 | 구간 | 담당 내용 | 연결되는 대면 평가 |
| --- | --- | --- | --- |
| 0:00~0:45 | 문제와 목표 사용자 | 반복되는 공유 자료 준비 문제와 사용자를 한 사례로 설명 | 아이디어 전달력 및 문제 해결력 |
| 0:45~1:35 | 해결 방식 | AI 제안, 사람의 공개 범위 확인, 새 공유본 작성 흐름 설명 | 아이디어 전달력 및 문제 해결력 |
| 1:35~2:20 | 직접 개발 범위 | 외부 모델 호출과 직접 구현한 계약/검증/변환 경계를 구분 | 기술 구현력 및 라이브 시연 완성도 |
| 2:20~3:50 | 라이브 시연 1 | 입력/승인 정보를 준비하고 검증된 실행 경로를 시연 | 기술 구현력 및 라이브 시연 완성도 |
| 3:50~5:20 | 라이브 시연 2 | 결정적 변환/검토 결과와 재현 가능한 toy 실행을 시연 | 기술 구현력 및 라이브 시연 완성도 |
| 5:20~6:15 | 적용 가능성 | 실제 적용 조건과 비교 실험 계획 또는 측정 결과를 제시 | 적용 가능성 및 확장성 |
| 6:15~7:00 | 확장과 마무리 | Rule과 공개 SkillPack의 확장 범위를 구분하고 핵심 메시지 회수 | 적용 가능성 및 확장성, 발표 구성 및 팀워크 |

라이브 구간은 합계 3분을 확보한다. 각 구간의 주 담당자와 장애 시 설명/재생 전환을 맡을 백업 담당자를
리허설 전에 정한다. 현장 시연이 실패하면 성공으로 꾸미지 말고, 확인된 마지막 상태와 실패 지점을
짧게 설명한 뒤 사전에 검증한 백업 자료로 전환한다.

질의응답 5분은 다음 네 축으로 역할을 나눈다. 아이디어/사용자 질문, 직접 개발/시연 질문,
적용/확장 질문, 구현 범위/한계 질문의 주 답변자를 정하고 다른 팀원은 근거 파일이나 화면을 찾는다.
답변은 현재 구현, 설계 목표, 사업성 가설을 구분하며 모르는 운영 수치나 외부 모델 성능을 만들지 않는다.

## 핵심 메시지와 동선

"기업이 외부 도움을 요청할 때, 무엇을 공개할지 정하고 공유 자료를 다시 준비하는 수고를 줄인다"로
시작한다. 공개 범위를 사람이 확인한다는 축을 유지하고, 화면의 모든 버튼이 연결됐다고 설명하지 않는다.

| 구간 | 전달할 메시지 | 발표 근거/주의할 구분 | 주요 평가 항목 |
| --- | --- | --- | --- |
| 문제/사용자 | 문의하려고 자료를 가리고 다시 쓰는 반복 작업 | 뉴스는 문제의 배경. 제품의 효과 측정 자료와 구분 | 기획의 구체성, 아이디어 전달력 |
| 흐름 | AI 제안 -> 사람이 범위 확인 -> 새 공유본 작성/검토 | 전체 흐름은 설계 목표. AI 생성 선택지와 A~D는 ISSUES PRES-06 참조 | 기획의 창의성, 문제 해결력 |
| 기술/데모 | 승인 정보의 작성/검토, 결정적 변환, 고정 toy 재현 | 현행은 외부 README/API가 기준. 실제 실행/fixture/녹화 재생을 구분 | 기술 완성도, 기술 구현력/시연 완성도 |
| 재사용/확장 | 공개 기준 데이터와 공개 에이전트 스킬 | 사내 Rule의 승인 권한과 공개 SkillPack 설치를 섞지 않음 | 적용 가능성 및 확장성 |
| 기대효과 | 준비 시간/누락/재질문 감소를 검증할 수 있다 | 측정 전에는 기대/가설. 작은 비교 실험으로 근거 준비 | 성과 및 실용 가능성 |
| 시장/마무리 | 기업 업무에 적용할 수 있는 솔루션 형태로 확장 가능 | B2B 포장은 의도된 발표 전략. 시장 숫자는 출처/가격/도입률 가정 명시 | 적용 가능성 및 확장성, 발표 구성 |

실제 제품 효용에서 비중이 작아도 인상적인 실행 경계/도식/예제를 강조할 수 있다. 실제 가치 평가와
발표 강조 순서는 별개다. 현재 구현/향후 기능/사업성 가설의 구분은 유지한다.

## 시장 규모를 방어할 최소 근거

현재 슬라이드의 숫자는 검증된 매출 전망이 아니라 단순 가정 계산이다. 보완 사항은
[ISSUES PRES-09](ISSUES.md)에 모으고 같은 시장 정의를 다른 문서에 별도로 복제하지 않는다.

- SAM 3,600억 원은 150,000개사 * 월 200,000원 * 12개월이다. 모두 구매하는 연간 지출
  잠재량이며 실제 도입률이 반영된 전망이 아니다. 기업 수는 통계 원문 URL/기준 연도/업종/규모/
  중복 제외 기준을 기록한다. 해당 기업들이 정말 자료 반출 준비 수요와 사내 AI 환경을 갖췄는지 좁힌다.
- 월 20만 원은 현재 가격 가정이다. 실제 계약/지불 의사/경쟁 가격 등의 근거가 없으면 가정이라고
  적는다. 제품에 과금 기능이나 확정된 구독 BM이 있다는 뜻으로 말하지 않는다.
- SOM 360억 원은 위 모집단의 10%, 즉 15,000개사를 잡은 시나리오다. 단순 비율 외에 기간/
  접근 가능한 고객군/도입 가능 환경/유통/지원 역량을 붙여 실제 도달 가능한 비율을 설명한다.
- TAM의 '약 12배'에는 국가 범위/기업 수/구매 조건의 근거가 없다. 같은 범위의 통계로 다시
  계산하거나 근거 없는 배수는 보류한다. 산술상 3,600억 * 12는 4.32조이며 기존 4.2조와도
  정확히 일치하지 않았다. 이번에 슬라이드의 산술을 4.32조로 맞췄으며 배수 자체의 근거는 여전히
  미확인이다. 기업 수 * 단가 방식의 표기도 상향식(Bottom-up)으로 바로잡았다.

최소한 기업 수 출처/가격 가정/기간을 둔 도입률 중 하나라도 보강하면 현재보다 설명이 단단해진다.
최종 발표에는 세 축 모두 드러내는 것이 목표다. 예를 들어 SAM 가정에서 1%/5%/10% 도입이면
각각 연 36억/180억/360억 원이다. 이 수치는 계산 예시이며 도입률의 실증 근거가 아니다.

## 기대효과를 방어할 작은 실험

'Zero', '원클릭 갱신', 눈금/수치 없는 막대는 현재 주장/도식이다. 측정 결과처럼 제시하지 않는다.
[가치 비교 정본](../prd.md)의 같은 조건 원칙을 따르고, 준비할 최소 실험은 다음과 같다.

1. 가상 로그 10건과 같은 문의 목적/수신처/공개 조건/필수 단서를 고정한다. 각 로그의 공개 금지
   항목과 반드시 남겨야 할 단서를 사람이 사전에 표시한다. 실제 회사 자료를 새로 수집하지 않는다.
2. 같은 자료를 직접 준비하는 방식과 SafeHandoff로 준비하는 방식으로 처리한다. 실행 순서를
   번갈아 학습 효과를 줄이고 참여자/날짜/코드 판본/지침/모델/모드를 기록한다. 일반 AI 비교를
   추가하면 같은 사내 모델/기준/지침/도구/수정 기회를 제공한다.
3. 건별 사람 작업 시간, 모델/서버 대기 시간, 총 경과 시간을 분리한다. 가리지 못한 금지 항목 수와
   지워서 잃은 필수 단서 수를 따로 세고 수정 횟수/최종 통과 여부도 남긴다. 가림 개수만으로 효용을
   판단하지 않는다. 의미 판정은 사전 기준에 따른 사람 검토이며 LLM 평가/문장 정규식 회귀로 대체하지 않는다.
4. 현행 UI에서 연결되지 않은 단계는 성공 처리하지 않는다. API/CLI와 사람이 조립한 결과라면
   그 개입을 기록하고 '부분 파이프라인 실험'으로 발표한다. 목업의 클릭 수를 사람 작업 시간으로
   대신하지 않는다. 실패/보류도 10건의 분모에 포함하고 미완료 사례의 시간을 임의 보정하지 않는다.
5. 원자료별 측정표를 남기고, 같은 완료 조건을 충족한 사례의 중앙값/범위와 전체 성공/실패 수를
   함께 제시한다. '10건에서 놓친 금지 항목 0개'가 나와도 일반적인 유출 Zero 보장으로 확대하지 않는다.

측정표의 권장 열은 case_id / 방식 / 모드/수동 개입 / 사람 작업 초 / 대기 초 / 전체 초 /
노출 잔존 수 / 필수 단서 누락 수 / 수정 횟수 / 완료 상태다. 아직 이 10건 실험을 실행하지 않았으며,
수치나 감소율을 이 가이드에서 만들어 넣지 않는다. 실제 로그는 로컬 평가 결과에, 발표에는 집계와
가상 데이터 범위만 반영한다. 기존 Docker 성공은 시간 절감/사용자 효용의 증거가 아니다.

## 질문 대응과 편집 주석

- "왜 B2B 솔루션인가?": 기업의 자료 준비 문제를 설명하는 발표 프레임이다. 현행 제품은 내부
  설치 오픈소스이며 구독료는 시장성 시나리오의 가정이라고 설명한다.
- "다 구현했나?": 정본의 실제 연결 범위를 답하고 목업/계획/실제 실행을 구분한다.
- "기존 AI보다 얼마나 좋은가?": 동일 조건 실험의 측정값만 답한다. 미측정이면 검증 계획을 말한다.
- "정보 유출이 0인가?": 사람의 공개 결정과 현재 기준 검사로 준비를 돕는 것이며 보장하지 않는다고 답한다.

`// DECISION: [PRES-DEC-01]`은 B2B 포장의 의도된 편집 결정을 뜻한다. 구현 누락 TODO가 아니다.
`// TODO: [PRES-번호]`는 실제 미완료/근거 미확인 항목이다. 같은 페이지에 두 종류가 함께 있을 수
있다. HTML에 결정을 다시 길게 적지 않고 외부 decisions 문서를 참조한다.

이전 Go fixture 시제품의 CDP 녹화를 사용할 때는 [영상 참고자료](video/README.md)의 출처/
모드 표시를 따른다. 현재 앱에서 방금 실행한 결과처럼 소개하지 않는다.
