# F06 Rule 재사용 — 본체 계획의 시작 (제안/검색 메모)

`docs/next-round-plan.md`가 F06 본체(서버 `rules` 테이블·scope 매칭·철회/만료 전파)를 "큼, 별도
기능"으로 남겨둔 그 작업의 전용 계획 문서다. [review-grounding-plan.md](review-grounding-plan.md)는
F06 §2("서버만 현재 입력과 기준을 매칭한다")를 Engine 쪽에서 독립 재검증하는 **결정적** 경로만
구현했고, §4에서 "Rule 매칭 자체는 범위 밖"이라고 명시했다. 이 문서는 그 범위 밖 작업 중
하나인 "Rule 제안(검색)" 설계만 적는다. 아직 구현하지 않았다.

## scope의 `skill_set_hash` 용어 확인

`rule.v1`/`decision.v1`의 scope 필드 `{project_id, purpose_id, recipient_id, audience,
skill_set_hash}` 중 `skill_set_hash`는 Rule이라는 엔티티 이름과 무관하다. 이건
`packages/skill-loader/src/index.ts`의 `skillSetHash()`가 만드는, **그 작업에 활성 상태였던
SkillPack들**(F07, `.agents/skills` 관례를 따르는 팩)의 `(id, version, pack_sha256)` 정렬 목록
해시다. 활성 팩이 analyst/writer/reviewer 프롬프트와 도구 권한을 바꾸므로, 다른 팩 구성에서
승인된 Rule을 지금 팩 구성에 그대로 재사용하면 안 된다는 조건을 scope 비교에 넣은 것이다.
기존 문서(`features/06-decision-reuse.md`, `review-grounding-plan.md`, `contracts/rule.v1.schema.json`,
`grounding.ts`)는 전부 이 필드를 scope 안의 값으로만 쓰고 있고, Rule 전체를 "스킬 집합"으로
잘못 부르는 곳은 없었다 — 확인 결과만 기록한다.

## 두 갈래: 결정적 적용 vs 비기계적 제안 — 기존 문서가 실제로 말하는 것과 이번에 추가하는 제안의 경계

**정정**: 이전 판에서 이 절에 "판정자: 리뷰 에이전트(LLM)의 정성적 판단"이라고 단정적으로
적었는데, 기존 문서를 다시 대조해보니 그 주체·단계를 명시한 곳이 없다. 과장이었다 — 아래는
실제로 쓰여 있는 문장과, 그걸 근거로 이번에 **새로 제안하는 설계(아직 미확정)**를 명확히
나눈 것이다.

### 기존 문서가 실제로 말하는 것 (그대로 인용)

- `features/06-decision-reuse.md:15` — "**모델**은 비슷한 기준을 제안할 수 있지만 활성 규칙을
  만들거나 범위를 늘리지 못한다." 주체가 "모델"로만 되어 있고 분석/작성/검토 중 어느 단계인지
  특정하지 않는다.
- 같은 문서 §7 — "임베딩 유사도에 의한 자동 공개 허가 ... 는 제외한다. **일반 문서 유사 사례는
  선택 제안까지 허용한다.**" 역시 주체·단계 불특정.
- `AC-F06-04` — "일반 문서의 유사 후보는 사용자 적용 전까지 허용 상태가 아님." 제안이 자동
  승인은 아니라는 것만 확인하고, 어느 단계가 제안을 만드는지는 말하지 않는다.
- `review-grounding-plan.md` §3이 리뷰 에이전트에 실제로 맡긴 역할은 이것과 **다르고 더 좁다**
  — "문장이 과거 자료를 은근히 베낀 것처럼 보이는가" 같은 애매한 경우를 **방어적으로 걸러내는**
  것(초안이 근거 없이 "이전과 동일" 같은 표현에 의존하면 반려)이다. 이건 "유사 Rule을 찾아
  적용을 제안"하는 게 아니라 반대 방향(근거 없는 재사용 냄새가 나면 거부)이다.

세 문서를 모두 모아도 "리뷰 에이전트가 비기계적 유사도로 Rule을 검색해 질적 판단으로
제안한다"는 문장은 어디에도 없다. "모델이 비슷한 기준을 제안할 수 있다"는 오히려 F03의 공개
결정 화면(UI-04, `proposeDisclosure`)이 사용자에게 표현 방식을 고르도록 돕는 흐름에 더
자연스럽게 들어맞는다 — 리뷰는 이미 작성된 초안을 사실 단위로 검증하는 단계라 "아직 결정되지
않은 Rule 적용 여부"를 처음 제안하는 자리로 보기 어렵다.

### 이번에 추가로 제안하는 설계 (미확정, 구현 전 결정 필요)

| | 결정적 적용 (기존 스펙, 구현 완료) | 비기계적 제안 (신규 제안, 미구현) |
| --- | --- | --- |
| 대상 | scope가 **정확히** 일치하는 Rule | scope가 정확히 일치하지 않거나 애매한, "비슷해 보이는" 과거 Rule |
| 판정자 | 코드 (`grounding.ts`의 `scopeValid`/`canonical` 비교) | **미정** — F03 `proposeDisclosure`(공개 결정 제안 단계) 또는 리뷰 단계, 둘 중 어디에 붙일지 결정 필요 |
| 근거 문서 | `features/06-decision-reuse.md` §2, `review-grounding-plan.md` | 없음 — 위 "기존 문서가 실제로 말하는 것"에서 추론한 확장 제안 |
| 결과 | `applied_rule_id`/`version`으로 grounding, 사람에게 다시 안 물음 | "참고할 만한 선례가 있다"는 제안만, 최종 반영은 여전히 fresh decision 취급 |
| 상태 | 구현 완료([review-grounding-plan.md](review-grounding-plan.md)) | 미구현, 어디에 붙일지도 미정 |

어디에 붙이든 제안 경로는 결정적 grounding을 우회하지 않는다 — 과거 Rule을 "참고"했다고 그
fact가 `reused_rule`로 grounding되지는 않으며, 여전히 `fresh_decision`으로 취급되고 사람의 새
승인이 필요하다. 제안은 판단 재료일 뿐이다. **판정자를 리뷰 단계로 할지 F03 제안 단계로 할지는
아직 결정하지 않았고, 이 문서는 그 선택을 미리 확정한 것으로 보지 않는다.**

## 검색 수단: Mem0 대신 sqlite-vec로 충분한지

**결론: 이 좁은 용도엔 sqlite-vec만으로 충분하다.** Mem0가 주는 것 중 여기서 쓸 건 "벡터
유사도 검색" 하나뿐이고, 나머지(LLM 기반 사실 추출·기억 통합/중복 판정·그래프 관계)는
Rule이 이미 `rule.v1`으로 구조화돼 있어서 필요 없다.

sqlite-vec가 주는 것:
- `vec0` 가상 테이블로 벡터 저장 + `vec_distance_cosine` 등으로 KNN 검색.
- 순수 C 확장이라 네트워크 호출 없음(오프라인 요구와 맞음), `better-sqlite3`(이미 `TaskStore`가
  씀)에 `db.loadExtension()`으로 바로 붙는다.
- Rule 개수가 적을(수백~수천) 이 쓰임에서 brute-force KNN 성능은 문제가 안 된다.

sqlite-vec가 안 주는 것(직접 써야 할 코드):
1. **임베딩 생성 자체** — Rule 저장 시 `selector + representation.kind + statement 요약`을
   벡터로 바꿀 임베딩 호출이 필요하다. 지금 설정된 `provider`(OpenAI-compatible 엔드포인트)가
   `/embeddings`를 지원하는지 아직 확인 안 했다 — 안 지원하면 별도 로컬 임베딩 모델을 config에
   추가해야 하는 실제 운영 비용이 생긴다. 이건 가정하지 않고 구현 전에 먼저 확인해야 한다.
2. **저장 글루**: Rule을 새로 만들거나 판본이 바뀔 때 임베딩을 계산해 `vec0` 테이블에
   `rule_id`로 연결해 넣는다. 철회된 Rule은 조회 시 제외하거나 삭제한다.
3. **조회 글루**: 현재 후보의 statement/context를 같은 방식으로 임베딩 → KNN top-k →
   `rules` 테이블 join → 결과를 "참고 후보"로만 **소비 단계(F03 제안 또는 리뷰 — 위 "미확정"
   참고)**의 프롬프트에 넣는다(grounding 필드에는 넣지 않음, §"두 갈래" 표의 구분 유지).
   이 글루 자체는 어느 단계가 소비하든 동일하므로, 판정자를 아직 정하지 않았어도 검색
   메커니즘 설계는 미리 해 둘 수 있다.

## 범위에서 빼는 것

F06 본체(실제 `rules` 테이블 스키마, scope 매칭 엔진, 철회/만료 전파, UI-04/08)는 여전히
[next-round-plan.md](next-round-plan.md)의 별도 큰 작업이다. 이 문서는 그중 "제안 검색"
서브토픽의 설계 방향(Mem0 불필요, sqlite-vec + 소량 글루)만 기록했고, 실제 테이블 스키마·
임베딩 호출 연결·프롬프트 반영은 구현하지 않았다. **제안을 소비하는 단계(F03 제안 vs 리뷰)도
아직 결정하지 않았다** — 이 선택은 기존 스펙에 쓰여 있지 않으므로 구현 전에 담당자 결정이
필요하다.
