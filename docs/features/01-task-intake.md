# F01 - 목적과 자료 준비

상태: 입력 화면 개편 설계, 미구현 / 기준일: 2026-11-01 / 구현 담당: [plan.md](../product/plan.md)의 F01 담당

## 1. 목적

[PRD-04](../product/prd.md)의 공유 자료 준비를 시작하는 화면이다. 사용자는 어떤 상황에서
어떤 도움을 받고 싶은지 설명하고 관련 원자료를 모은다. 앱은 그 맥락을 바탕으로 분석과 공개 질문을
준비한다. 미리 정해진 분류를 모두 채우게 하는 것이 이 화면의 목적은 아니다 (`INT-01`~`INT-04`).

완료 지점은 필수 설명과 사용할 원자료를 저장해 분석할 수 있게 만드는 곳이다.
설명·파일 등록·목적 선택은 공개 허가나 외부 전송 지시가 아니다. 이 단계에서 문서를 작성하거나 발송하지 않는다.

이 문서는 다음 구현의 입력 설계다. 현재 화면과 HTTP API는 여전히 제목·목적·수신처·공개 범위를
필수로 받고 설명 필드는 없다. 아래 개편을 구현 완료로 해석하지 않는다.

## 2. 쓰는 사람과 권한

| 주체 | 허용 | 금지 |
| --- | --- | --- |
| 현재 로컬 세션 사용자 | 자기 앱의 작업 생성/입력 변경/자료 등록/제외/내부 미리보기 | 유효하지 않은 세션/CSRF 요청, 다른 task 객체를 섞은 참조 |
| F02 분석 실행 | 서버가 고정한 현재 작업 자료를 읽기 | 원본 바이트 수정, 수신자 변경, 공개 승인 |
| 작성 모델 | 이 기능의 원자료 API 접근 없음 | 원자료/전체 파일 목록 조회 |
| 외부 수신자 | 권한 없음 | 작업 목록/원자료/내부 이름 조회 |

단일 사용자 PoC에서도 모든 자료/근거 요청의 task 소속을 서버에서 검사한다. UI에서 버튼을 숨기는 것만으로 권한 처리를 끝내지 않는다. 인증/로컬 접근의 구체 규칙은 [F10](10-runtime-boundary.md)을 따른다.

## 3. 화면과 사용자 동작

사용자 흐름의 `01 목적과 자료`에 적용한다. IA의 UI-02는 논리 화면 식별자이며
별도 URL 구현 완료를 뜻하지 않는다. 기존 작업은 목록에서 열어 설명과 자료를 확인한다.

### 입력과 화면 설명

화면 안내: `어떤 상황이고 어떤 도움을 받고 싶은지 설명하고, 관련 자료를 추가하세요.`

| 입력 | 필수 여부 | 용도와 안내 |
| --- | --- | --- |
| 설명 | 필수 | `어떤 자료를 만들고 싶나요?` 상황, 받고 싶은 도움, 목표, 상대가 알아야 할 점, 공개 가능한 범위와 제약을 자유롭게 적는다. 모두를 빠짐없이 쓰도록 요구하지 않는다. |
| 제목(label) | 선택 | 목록에서 이 작업을 구분하는 내부 이름이다. 비워도 생성·분석을 막지 않는다. 작업 ID 등 내부 식별자로 구분하며 공개 문서 제목으로 그대로 사용하지 않는다. |
| 전달 목적 | 선택 | 설명을 보충하는 문의 유형 힌트다. 선택하지 않아도 진행한다. 아래 선택지의 취지와 한계를 함께 설명한다. |
| 공개 범위 | 선택 | 기존 `공개`/`지정 외부 수신자` 선택은 설명을 보충하는 맥락이다. 미선택을 공개나 허용으로 간주하지 않는다. |
| 원자료 | 분석 시 1개 이상 | 지원 파일을 추가하고 사용 여부를 확인한다. 자료 선택·등록만으로 모델을 호출하지 않는다. |

수신처와 목표는 독립 필드에서 제거한다. 상대나 원하는 결과가 중요하면 설명에 자연어로 적는다.
목적과 공개 범위도 설명에서 다룰 수 있으므로 같은 내용을 반드시 별도 선택으로 반복하지 않는다.
설명이 빈 문자열 또는 공백뿐이면 설명 입력을 안내한다. 선택 입력 미작성은 오류가 아니다.

설명 예: `응답 지연 상황을 공급사에 문의할 자료가 필요합니다. 원인과 다음에 확인할 내용을 묻고 싶습니다.
고객명과 내부 주소는 빼고 추이는 전달하고 싶습니다.` 이 문장은 예시이며 기본 입력·공개 승인으로 저장하지 않는다.

1. 설명을 적고 관련 원자료를 추가한다. 제목·전달 목적·공개 범위는 필요할 때만 보충한다.
2. 작업과 자료를 저장한 뒤 분석을 명시적으로 시작한다. 저장과 분석 결과를 구분한다.
3. 분석은 설명을 맥락으로 사용하되 목표·상대·공개 조건의 해석을 확정된 공개 결정으로 저장하지 않는다.
4. 선택값과 설명이 충돌하거나 실제 공개 결정에 필요한 조건이 불명확하면 해당 단계에서 사용자에게 묻는다.
   모호하다는 이유만으로 입력 화면에서 모든 분류를 강제로 채우게 하지 않는다.
5. 자료 저장 후 분석 접수가 실패해도 설명·자료는 남기고 분석만 재시도한다.

### 전달 목적 선택지는 왜 세 종류인가

현재 구현은 `packages/server/src/workflow-catalog.ts`에 다음 세 종류를 고정한다.
아래 연결은 `INT-03`의 사례로 설명할 수 있는 취지이며, 이 세 분류를 확정한 사용자 의사결정의 근거는 확인되지 않았다.

| 현재 선택지 | 예상 용도 | 분류의 한계 |
| --- | --- | --- |
| 오픈소스 버그 제보 (`oss_issue`) | 메인테이너가 현상·환경·재현 또는 미확인 사항을 이해할 제보 자료 | 오픈소스는 도움을 구하는 경로이고 버그 제보는 요청 성격이다. 다른 문의와 배타적이지 않다. |
| 기술지원 문의 (`vendor_support`) | 공급사에 현상과 질문을 전달할 지원 자료 | 공급사 지원에서도 버그 제보와 운영 자문을 함께 요청할 수 있다. |
| 운영 자문 (`operations_advice`) | 운영 상황을 설명하고 외부 조언을 구할 자료 | `INT-03`의 일반 내부 자료 자문·설명을 운영 업무로 좁힐 근거가 부족하다. |

세 가지는 초기 사례를 설명하는 보조 선택지일 뿐, 제품이 처리할 수 있는 목적의 전체 목록이 아니다.
세 가지 중 하나를 필수로 고르게 하거나 일반 설명 요청을 배제하면 사람의 준비 부담을 줄이고
일반 자료에도 적용하려는 `INT-02`·`INT-03`에 맞지 않는다. 설명만으로 시작할 수 있어야 한다.
선택지는 초기 연결을 설명하기 위해 문서에 남기며 그대로 유지해야 할 제품 방향으로 확정하지 않는다.

### 빈 화면/실패 화면

| 상태 | 화면 동작 |
| --- | --- |
| 새 작업에 자료 없음 | 형식 안내/붙여넣기 제공, 분석 비활성 |

| 설명과 선택값 충돌 | 값을 조용히 덮어쓰지 않고 관련 분석·공개 결정에서 해석을 확인 |

| 네트워크 불명확/중복 클릭 | 같은 멱등 키로 결과 조회/재시도. 작업을 중복 생성하지 않음 |
| 오래된 revision | 현재 선택이 바뀌었음을 표시, 입력 보존 후 최신 상태 조회 |

## 4. 데이터: 읽고 쓰는 표/칸

정확한 열/제약은 [ERD](../design/erd.md)를 따른다.

| 데이터 | 읽기 | 쓰기 / 제약 |
| --- | --- | --- |
| 목적 선택지 | 선택 입력의 표시 이름과 용도 | 사용자 의도나 공개 허가를 대체하지 않음. 세 종류의 적합성은 위 TODO 대상 |
| tasks | 현재 revision/phase/scope/포인터 | description(필수), internal_title/label·purpose_id·audience(선택), 자료 집합, revision, phase |
| task_snapshots | 현재 입력 범위 | 설명·명시한 맥락/자료 집합/지침 판본의 불변 스냅샷 |
| source_versions | 기존 source_id/버전 | 원본 raw_bytes, sha256, format, display_name, source_slot, parser_version; 변경은 새 version |
| task_sources | 현재 사용 자료 | current_source_version_id, included. 제외는 원자료 바이트 수정이 아님 |
| jobs / artifacts / exports | 이전 실행/현재 결과 | 입력 변경에 따른 취소 요청/stale 표시/현재 결과 무효화 |
| events / idempotency_keys | 중복 요청/현재 이벤트 순서 | 상태 변경 이벤트와 응답 기록을 같은 트랜잭션에서 저장 |

설명/원자료의 파일명/내부 작업 이름은 공개 데이터가 아니다. F02와 내부 UI는 필요한 범위에서 읽지만 F04 작성 입력에 그대로 복사하지 않는다.

## 5. 입력/상태/동시성 규칙

### 입력 계약

- 설명은 필수이고 제목(label)·전달 목적·공개 범위는 선택이다. 수신처·목표 입력 필드는 없다.
- 선택 입력의 공백/미선택은 유지한다. 기존 필수 API를 통과시키려고 가상 수신처나 기본 목적을 만들지 않는다.
- 설명 속 목표·목적·상대·공개 조건은 분석의 맥락이며 공개 허가는 아니다. 원문 사용에는 별도 사용자 결정이 필요하다.
- 설명 원문을 작성기에 그대로 전달하거나 공유 파일에 복사하지 않는다. 공개할 설명 내용도 후보와 공개 결정을 거친다.
- 공개 범위가 없거나 모호하면 자동으로 `public`·`named_external`을 채우거나 과거 재사용 규칙의 범위에 합치지 않는다.

<!-- // TODO: description 저장·분석 입력, 선택값의 미지정 표현, 기존 scope/규칙 재사용과의 관계를 API·저장소·코어 계약에서 설계한다. 기존 recipient_id/goal_variant를 설명으로부터 자동 확정하는 우회 구현은 하지 않는다. -->

- 출력 언어는 PoC 기본 `ko`/`en`이다. 다른 값은 명시적 지원 없이 통과시키지 않는다.
- 자료는 UTF-8 `.txt/.log/.md/.csv/.json`과 붙여넣기를 지원한다. 파일 형식과 내용 파싱 결과를 모두 확인한다.
- PoC 기본 제한은 작업당 현재 자료 10개, 파일당 262,144바이트, 현재 자료 합계 1,048,576바이트다. 모델 문맥 제한은 별도다. 조정값의 권위는 [spec](../design/spec.md)의 limits다.
- 원본의 UTF-8 바이트를 보존한다. 저장 전에 줄바꿈/Unicode 정규화/내용 치환을 하지 않는다. UTF-8 BOM 처리가 필요한 파서도 원본은 그대로 둔다.
- JSON의 중복 키/알 수 없는 계약 키/후행 JSON은 해당 구조 계약에 따라 거부한다. 일반 자료 JSON 자체의 키 집합과 제품 계약의 키 집합을 혼동하지 않는다.
- CSV는 중복 헤더/행 열 개수 오류를 표시한다. 잘못된 행을 조용히 버리지 않는다. 등록 스키마 `requests_v1`은 `observed_at,count`, source_slot은 `request_summary`이며 count는 0 이상의 정수다. 시각/단위가 읽혔다고 공개 허용되는 것은 아니다.
- 붙여넣은 내용은 명시적인 파일 항목으로 저장한다. 빈 텍스트만으로 분석을 시작하지 않는다.
- 같은 파일 표시 이름은 허용하고 source_id로 구분한다. 같은 내용 재첨부를 기존 자료 교체로 추정하지 않는다. 교체는 replace_source_id가 지정된 경우만 수행한다.
- 파일 표시 이름은 UI용이다. 사용자 문자열을 서버 파일 경로나 공개 파일 경로로 사용하지 않는다.

### 원자성과 판본

| 동작 | 결과 |
| --- | --- |
| 작업 생성 | revision 1, `needs_analysis`, 원자료 0개 허용 |
| 한 배치의 자료 추가/교체 | 모든 항목 검증 성공 시 한 트랜잭션, revision +1, `needs_analysis` |
| 한 항목 검증 실패 | 배치의 자료/포인터/revision 모두 변경 없음 |
| 현재 자료 제외 | included=false와 revision +1, 기존 결과 stale, `needs_analysis` |
| 설명 또는 전달 목적 변경 | revision +1, 현재 분석/결정 결과를 재사용하지 않고 재분석 |
| 공개 대상 조건 또는 공개 범위 변경 | revision +1, 기존 공유 허용은 새 범위에서 미유효, 결정 재확인 |
| 언어/지침 변경 | revision +1, 결과 stale. 지침 변경의 재분석 여부는 공통 전이표에 따름 |
| 제목(label)만 변경 | 내부 식별용 변경으로 취급. 분석 맥락이나 공개 허가로 해석하지 않음 |
| 원문 같은 위치의 새 파일 교체 | 새 source_version. 이전 exact/raw 허용 자동 이전 불가 |

상태의 최종 적용은 [spec](../design/spec.md)의 전이표가 결정한다. 이전 job 취소가 늦어져도 CAS가 오래된 결과 적용을 차단한다. 사용자 입력 저장은 이전 모델 호출 종료를 기다리지 않는다.

### 멱등/경쟁

모든 변경 요청은 Idempotency-Key와 필요한 expected_revision을 사용한다. 같은 요청을 같은 키로 재전송하면 원래 결과를 반환한다. 다른 본문에 같은 키를 쓰면 409다. source-batches를 포함한 배치의 변경은 한 번만 적용된다. 여러 창의 오래된 요청은 최신 값을 덮어쓰지 않는다.

## 6. 다른 기능과 닿는 곳

REST 경로와 DTO의 최종 정의는 [api.md](../design/api.md)다. 논리 서비스 이름은 아래와 같이 고정한다.

| 서비스 / API | 입력 | 반환 / 다음 기능 |
| --- | --- | --- |
| `TaskService.CreateTask` / `POST /api/v1/tasks` (개편 설계) | description 필수, label/internal_title·purpose_id·audience 선택. 정확한 DTO는 미정 | task_id, revision, phase -> F02/UI |
| `TaskService.UpdateTask` / `PATCH /api/v1/tasks/{id}` | expected_revision과 명시적으로 수정하는 metadata/scope | 최신 revision, phase, 허용 action, 무효화 요약 |
| `SourceService.AddSourceBatch` / `POST /api/v1/tasks/{id}/source-batches` | multipart `meta`: expected_revision, items(client_key, display_name, format, source_slot, replace_source_id); 파일 필드 이름은 client_key | source_versions, current_revision, invalidated_artifact_ids, phase |
| `SourceService.ExcludeSource` / `DELETE /api/v1/tasks/{id}/sources/{source_id}` | expected_revision | 최신 입력 집합, phase |
| 내부 자료 조회 / `GET /api/v1/tasks/{id}/sources/{source_version_id}` | 현재 인증 세션, task/source 소속 | 내부 미리보기/판본/원본 해시 |
| catalog 조회 / `GET /api/v1/catalog` | 현재 인증 세션 | 목적 등 보조 선택지와 자료 제한. 프로젝트·수신처 사전 등록을 요구하지 않음 |

F02는 앱이 지정한 불변 source_version_id와 실제 바이트로 분석한다. F03는 해당 판본의 근거를 기반으로 결정한다. F04에는 원자료를 직접 넘기지 않는다. F09의 작업 삭제는 현재 입력에서 제외하는 동작과 다르다.

## 7. 하지 않을 것

PDF/DOCX/이미지/OCR/ZIP 자동 해제, URL 크롤링, 외부 저장소 자동 가져오기, 임의 로컬 경로 읽기, 다중 사용자 프로젝트 권한, 원자료 자동 공개, 업로드 내용을 자동 실행하는 기능은 없다. 파일 형식만 바꾸어 허용되지 않은 내용을 우회 실행할 수 있게 하지 않는다.

## 8. 끝났다는 기준

개편 설계의 수용 기준이다. 기존 파일 저장/판본 테스트는 설명 필수·선택 입력·제거 필드의 동작을 검증하지 않는다.
AC-F01-01은 이 미구현 범위를 반영해 수용 기준 추적표에서 partial로 표시한다.

| ID | 분류 | 실행과 기대 결과 |
| --- | --- | --- |
| AC-F01-01 | 정상 | 설명과 TXT/CSV/JSON 저장·복원. 제목/전달 목적/공개 범위 없이도 작업 생성·분석 가능 |
| AC-F01-02 | 정상 | 자료 추가/교체/제외가 각각 불변 과거 판본과 새 현재 집합을 유지하고 revision을 한 번 올림 |
| AC-F01-03 | 경계 | 파일 수/파일/합계 바이트 한도 정확히 이하는 허용, 1개/1바이트 초과는 배치 변경 없이 거부 |
| AC-F01-04 | 오류 | 깨진 UTF-8/JSON/CSV 또는 잘못된 파일이 한 배치에 있으면 전체 배치 미반영, 오류 항목 표시 |
| AC-F01-05 | 동시성 | 동일 멱등 요청은 한 번만 적용, 다른 요청의 키 충돌과 오래된 revision은 409 |
| AC-F01-06 | 권한 | 비인증 요청/다른 task의 source ID/위조 CSRF는 원자료를 읽거나 바꾸지 못함 |
| AC-F01-07 | 경계 | 파일명이 경로/HTML/제어문자를 포함해도 서버 경로로 사용하거나 코드로 실행하지 않음 |
| AC-F01-08 | 상태 | 설명/공개 조건/자료 변경 직후 이전 결과의 복사/확정 불가, 늦은 job이 현재 결과를 덮어쓰지 않음 |
| AC-F01-09 | 복구 | 자료 저장 후 모델 접수 실패 시 입력은 남고 분석만 재시도 가능 |
| AC-F01-10 | 의미 | 설명/원자료 업로드/제목(label)/내부 메모가 공개결정이나 작성기 공개 입력으로 자동 포함되지 않음 |

대응 시험은 [qa.md](../qa/qa.md)의 T10, T19, T25-26, T28-29, T43, T58이다.

## 9. 확인 필요와 구현 순서

실제 사내 수신자/반출 승인 조건은 Q-POLICY, 입력 자료의 실제 형식/제품 정보는 Q-EXT, 저장 위치/보존 운영은 Q-DEPLOY에서 확인한다. 가상 자료 개발은 이 정보 없이 시작한다.

구현 순서는 설명·선택 입력 계약 -> 저장/범위/재사용 규칙 정합성 -> 화면 개편 -> F02 맥락 전달·질문 -> 입력/복원/미지정 회귀 검증이다. 입력/판본 규칙을 바꾸면 spec/ERD/API/F02/F03/F09와 해당 시험을 함께 변경한다.
