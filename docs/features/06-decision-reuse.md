# F06 · 같은 조건에서 공개 기준 다시 쓰기

등급: P0 core · 담당: 정책/도메인 담당 · 의존: F01, F02, F03 · 연결: F04, F05, F09

이 파일은 [PRD](../prd.md), [spec](../spec.md), [ERD](../ERD.md), [API](../api.md)의 F06 구현 단위다. 기능 파일에만 새로운 권한 규칙을 만들지 않는다.

## 1. 목적

**같은 업무를 다시 할 때 표현 수준을 매번 처음부터 고르지 않게 하되, 새로운 자료의 내용은 다시 계산한다.** PRD-09를 구현하고 PRD-01의 준비 작업 감소를 검증한다. 지난 결과의 문장을 새 문서에 복사하는 기억 기능으로 만들지 않는다.

대표 예시는 ‘이 프로젝트에서 이 공급사에 문의할 때 요청량은 방향만 표시’다. 새 CSV에 820/780/1740이 들어오면 과거의 ‘계속 증가’를 쓰지 않고 감소·증가를 계산한다.

## 2. 쓰는 사람과 권한

인증된 로컬 사용자만 현재 결정에서 기준을 저장·변경·철회한다. 모델은 비슷한 기준을 제안할 수 있지만 활성 규칙을 만들거나 범위를 늘리지 못한다. 서버만 현재 입력과 기준을 매칭한다.

`exact_value`, `approved_excerpt` 승인은 재사용할 수 없다. 과거에 `attempt_id=att_demo_01`을 공개했다고 새 자료의 ID를 허용하지 않는다. 같은 원문 값이 다시 나타나도 새 source 판본은 별도 승인이 필요하다. 자유문서에서 모델이 ‘같은 주제’라고 한 결과도 자동 허가의 근거가 아니다.

## 3. 화면

| --- | --- | --- |
| UI-04 공개 선택 | ‘이번만’이 기본. ‘같은 조건에 재사용’ 선택 시 범위 문장을 표시 | 재사용 불가능한 정확값/원문은 이유와 함께 비활성화 |
| UI-03 작업 공간 | 적용한 기준 이름·판본·계산 결과·이번 자료의 근거 표시 | 일치 기준 없음이면 일반 선택 카드로 진행 |
| UI-08 저장 규칙 | 범위·변환·상태·만료·최근 사용을 표시, 수정·철회 | 아직 기준 없음: ‘선택을 저장할 때 재사용 기준을 만들 수 있습니다’ |
| UI-07 이력 | 어떤 작업에 어느 판본을 적용했는지 내부 기록 | 원자료 삭제 시 ‘원래 작업 삭제됨’, 과거 원문 재표시 금지 |

저장 전에 다음 범위를 한 문장으로 읽을 수 있어야 한다.

> 프로젝트 A에서 지정 공급사에 기술지원 문의를 보낼 때, 검증된 요청량 표의 건수는 공개하지 않고 관찰 순서와 증가·감소만 표시합니다.

‘이 선택 기억하기’ 하나로 공개 대상·목적을 넓히지 않는다. 수신자가 공개 이슈로 바뀌면 ‘이전 기준은 이 대상에 적용되지 않습니다’라고 표시하고 선택을 받는다. 철회 시 영향받는 진행 중 작업과 결과가 다시 확인 대상이 됨을 보여준다.

## 4. 데이터

| 표 | 읽기 | 쓰기 |
| --- | --- | --- |
| `rules` | id, version, scope, selector, transform, parameters, 만료·철회 | 새 불변 판본, 철회 시각 |
| `decisions` | 현재 공개 미리보기·허용 종류·source 참조 | 적용 결과에 `applied_rule_id/version`, 현재 투영 hash |
| `current_decisions` | 후보별 최신 결정 | 원자적 포인터 교체 |
| `tasks`, `task_snapshots` | project, purpose, goal_variant, recipient, audience, skill_set_hash, revision | 명시 적용·철회 영향 시 revision·상태 |
| `source_versions`, `candidates` | 검증된 schema·source_slot·필드 선택자 | 직접 수정 안 함 |
| `artifacts`, `exports`, `events` | 영향 범위 | stale·무효화·적용/철회 이벤트 |

원문·과거 공개 문장·실제 count·개별 ID를 기준 payload에 저장하지 않는다. 선택자는 `source_slot=request_summary`, `schema_id=requests_v1`, 필드 `count`처럼 앱이 파서로 확인할 수 있는 구조다. `source_slot` 이름만 같고 열·타입이 다르면 매칭하지 않는다.

## 5. 규칙

적용 불변조건은 INV-03·07·09·10·16이다.

### 저장

현재 유효한 `allow` 결정에서만 재사용 변환 기준을 만든다. `fact_summary`를 자동 재사용하려면 등록된 결정적 변환으로 다시 만들 수 있어야 한다. 자유롭게 쓴 요약 문장 자체는 자동 재사용 대상이 아니다. `derived_table` 등도 등록 selector·transform·parameters를 완전히 표현할 수 있을 때만 가능하다.

scope는 `project_id`, `purpose_id`, `goal_variant`, `recipient_id`, `audience`, `skill_set_hash`의 정확한 조합이다. purpose와 recipient의 의미가 바뀌면 표시 이름만 고치지 말고 새 ID를 만든다. 조사 목적을 관찰 정리로 줄이는 `goal_variant` 변경도 새 scope이며 과거 허용을 자동 이어받지 않는다. `expires_at=null`은 시간 만료 없음이며 source·scope·철회 조건이 없어지는 것은 아니다.

### 적용

1. 현재 작업의 scope와 현재 설치 팩 판본을 읽는다.
2. logical rule ID마다 최신 판본을 확인하고 활성·미만료·미철회 기준만 새 작업의 후보로 삼는다. 최신 판본을 쓸 수 없다고 과거 판본으로 자동 fallback하지 않는다.
3. scope를 정확히 비교한다. 일부 필드 누락을 wildcard로 해석하지 않는다.
4. 앱이 검증한 schema·필드·타입·조건을 확인한다.
5. 새 source bytes에서 변환을 다시 계산한다.
6. 현재 공개 미리보기와 hash를 만들고 적용한 rule id/version을 기록한다.
7. 결과와 범위를 UI에 표시하며 최종 파일 확인은 별도로 받는다.

새 분석 결과를 채택할 때의 자동 적용은 후보 집합과 파생 결정을 같은 트랜잭션에 저장한다. 입력 revision이 현재와 일치해야 한다. 이미 작업 중인 사용자가 새 기준 판본을 적용하는 동작은 revision을 한 번 올리고 결과를 무효화한다.

규칙이 여러 개 일치하고 서로 다른 공개 결과를 만들면 자동으로 더 많이 공개하는 쪽을 고르지 않는다. 해당 항목을 결정 필요로 돌린다. 같은 결과를 만드는 중복 기준은 출처를 모두 기록하되 공개 결정을 중복 생성하지 않는다.

### 수정·철회·만료

수정은 `expected_rule_version`을 검사하고 새 판본을 만든다. 다른 탭이 먼저 수정했으면 409 충돌이며 마지막 쓰기 우선으로 덮어쓰지 않는다. 새 판본이 과거 결정에 자동 소급 적용되지는 않는다.

첫 PoC의 철회는 해당 logical rule ID의 **모든 판본**에 적용한다. 그 판본들에 의존하는 현재 결정과 결과를 무효화하고 영향 작업의 revision을 올린다. 만료는 판본별이며 기존 결정을 이미 만들 때 사용한 판본의 유효성으로 검사한다. 최신 판본이 철회·만료되었다고 과거 판본을 새 작업에 자동 적용하지 않는다. 최신 결정이 철회됐다고 과거 허용으로 되돌아가지 않는다. 실행 시작·결과 채택·확정·다운로드에서 유효성을 다시 검사한다. 이미 사용자가 받은 파일은 회수하지 않는다.

## 6. 다른 조각과 닿는 곳

| 상대 | 주고받는 내용 | 서버 함수/API |
| --- | --- | --- |
| F03 공개 결정 | 유효 decision, selector, transform, 현재 미리보기 hash | `SaveRule`, `POST /api/v1/rules` 또는 decision batch의 재사용 옵션 |
| F02 분석 | 현재 후보 집합과 parser 인증 selector | `EvaluateReusableRules`, `ApplyReusableRules` |
| 사용자의 현재 작업 재적용 | `expected_revision`, `rule_refs=[{id,version}]` | `RuleService.ApplyToTask`, `POST /api/v1/tasks/{id}/rules/apply` |
| F04 작성 | 현재 rule 기반 결정을 투영한 fact_pack | 일반 승인팩 계약, 과거 문장 전달 금지 |
| F05 내보내기 | 적용 rule 판본의 현재 유효성 | 확정·다운로드 시 `ValidateApplicableRules` |
| F09 이력 | 적용·충돌·철회·만료 이벤트 | `GET /api/v1/rules`, `GET /api/v1/tasks/{id}/events` |
| 관리 | 새 rule 판본·철회 | `POST /api/v1/rules/{id}/versions`, `POST /api/v1/rules/{id}/revoke` |

모든 변경은 멱등 키와 해당 revision/version 검사를 따른다. 같은 키·같은 요청은 같은 결과, 같은 키·다른 요청은 `IDEMPOTENCY_CONFLICT`다. `rules/apply`는 하나라도 충돌하면 전체 결정을 적용하지 않고 `RULE_CONFLICT`를 반환한다. 독립 `POST /rules`는 출력 선택을 바꾸지 않아 source task revision을 유지하고, decision-batch의 규칙 저장은 그 선택 변경 commit에 함께 포함한다. scope·source·팩 변경 도중 계산이 끝나면 적용하지 않고 stale 처리한다.

## 7. 하지 않을 것

임베딩 유사도에 의한 자동 공개 허가, 정확한 값/원문 자동 재사용, 조직 전역 정책 상속, 서로 다른 수신자를 도메인명만으로 묶기, 과거 결과 그대로 복사, 선택을 기록하지 않는 장기 모델 기억은 이번 범위에서 제외한다. 일반 문서 유사 사례는 선택 제안까지 허용한다.

## 10. 구현 순서와 변경 영향
