# F09 - 진행/이력/중단 복구/작업 삭제

상태: P0 구현 기준안 / 기준일: 2026-10-31 / 구현 담당: [plan.md](../plan.md)의 F09 담당

## 1. 목적

[PRD-12](../prd.md)에 따라 사용자가 **지금 어디까지 됐고 무엇을 해야 하는지** 알 수 있게 한다. 저장한 선택을 새로고침/연결 끊김/프로세스 재시작에서 보존하고, 과거 실행이 현재 선택을 덮어쓰지 않도록 한다. 작업을 끝내거나 필요 없어진 자료는 명시적으로 삭제할 수 있게 한다.

이력의 목적은 준비 작업의 이해/복구/평가다. 전체 프롬프트를 항상 저장하거나 공개 첨부에 넣는 기능이 아니다.

## 2. 쓰는 사람과 권한

| 주체 | 허용 | 금지 |
| --- | --- | --- |
| 현재 사용자 | 작업 목록/이력 조회, 내부 과거 판본 보기, 실행 취소/재시도, 작업 삭제 | 비인증 조회, 다른 task 참조 혼합, 오래된 이력으로 공개 허용 복구 |
| workflow worker | 자신의 현재 job 상태/안전한 이벤트 기록 | 취소/삭제/교체된 job 결과를 현재 상태에 적용 |
| 모델 | 지정 호출의 응답 반환 | 이력 수정/삭제, 취소 취소, 승인 이벤트 생성 |
| 외부 수신자 | 없음 | 내부 trace/원자료/기록 접근 |

디버그 원문 기록은 운영 설정의 명시적 opt-in이며 기본 off다. 인증/저장 환경은 F10과 함께 구현한다.

## 3. 화면

UI-01 작업 목록, UI-03의 진행/이력 패널, UI-07(`/history`)에서 제공한다. 작업별로 현재 phase, 실제 job 단계, 시작/마지막 갱신 시각, 결정이 필요한 항목, 다음 가능한 행동, fixture/live 모드를 보여준다.

이벤트에는 사용자 선택/scope 변경, 적용 규칙, 작성/검토 시작/종료, 자동 수정, 수동 편집/검토, 확정, 취소/오류/중단을 구분한다. 시간이나 모델 사용량을 측정하지 못했으면 null/미측정으로 표시한다. 의미 없는 가짜 진행 퍼센트를 표시하지 않는다.

### 주요 동작

- `현재 작업으로 돌아가기`: 과거 기록을 현재 상태처럼 편집하지 않는다.
- `실행 취소`: 서버 취소 요청을 저장한다. 취소 완료가 확인되기 전에는 단순히 '완료'로 표시하지 않는다.
- `다시 시도`: 현재 revision으로 새 job을 시작한다. 이전 실패/사람 개입 기록을 삭제하지 않는다.
- `작업 삭제`: 대상 작업 이름/삭제 범위를 보여준 뒤 `DELETE` 입력과 저장 기준이 남는다는 확인을 받아 실행한다.

### 빈 화면/실패 화면

| 상황 | 표시 / 동작 |
| --- | --- |
| 기록 없음 | 아직 작업을 만들지 않았다는 안내와 새 작업 |
| 현재 작업에 실행 없음 | 자료/선택 상태와 분석/작성 시작 행동 |
| SSE 연결 끊김 | 연결 확인 중 표시, 현재 상태 조회, 중복 실행 요청하지 않음 |
| job 중단/실패 | 마지막 저장 단계, 안전한 오류, 입력 수정/설정 복구/재시도 경로 |

정확한 열과 연쇄 삭제는 [ERD](../ERD.md)를 따른다. 삭제는 앱이 내용을 다시 조회/내보내지 못하게 하는 계약이다. 이미 받은 파일/OS 백업 회수나 저장 매체의 복구 불가능한 삭제는 제공하지 않는다. debug 보존 정리는 서버 시작과 실행 중 주기 정리에서 수행하며, 정리가 지연된 경우 상태를 기록하고 원문을 계속 노출하지 않는다.

## 5. 상태/재시도/동시성 규칙

### 이벤트와 현재 상태

events.seq는 task 안에서 증가한다. 상태 변경과 이벤트 삽입은 같은 짧은 DB 트랜잭션이다. 이벤트는 UI 갱신 알림이며 현재 상태의 최종 권위는 DB의 task/job/artifact다. SSE만으로 '확정 가능'을 추정하지 않는다.

SSE는 Last-Event-ID로 재연결한다. 중복 이벤트는 무시하고 순서가 깨졌거나 요청한 이력이 없으면 현재 task 상태를 다시 조회한다. 현재 revision보다 오래된 이벤트가 결과를 되돌릴 수 없어야 한다. 새로고침은 현재 포인터와 결과를 조회하고 UI의 임시 상태로 서버를 덮어쓰지 않는다.

### job 실행과 취소

작업당 current_job_id는 하나다. 새 사용자 변경은 revision을 올려 이전 결과를 무효화한다. 내부 제목만 바꿔도 첫 PoC는 같은 보수적 규칙을 사용하며 UI에서 기존 결과를 다시 확인해야 함을 알린다. 긴 모델/도구 호출 중 DB 트랜잭션을 열어 두지 않는다.

취소 요청은 cancel_requested를 기록하고 가능한 모델/도구 실행을 중단한다. 물리적 호출 종료가 지연돼도 결과 적용 시 다음을 모두 검사한다.

- task가 아직 존재함.
- task.revision == job.input_revision.
- task.current_job_id == job.id.
- cancel_requested == false.
- scope/source/결정/규칙/지침 판본이 현재도 유효함.
- 검토 결과인 경우 target hash가 현재와 같음.

불일치 결과는 stale 또는 cancelled로 끝내고 현재 포인터를 바꾸지 않는다. UI도 오래된 응답을 적용하지 않는다. 같은 revision에서 재시도한 경우에도 current_job_id로 이전 실행을 구분한다.

### 재시작과 복구

프로세스 시작 시 이전 `queued`와 `running` job을 모두 `failed / INTERRUPTED`로 정리한다. 첫 PoC는 대기 작업을 자동 재개하지 않으며 사용자가 현재 상태를 확인한 뒤 새 job으로 명시적으로 재시도한다. 사용자 선택/원자료/완료 단계는 유지한다. 중간 파일이 존재한다는 이유만으로 finalized를 만들지 않는다.

재시도는 현재 revision과 typed arguments로 새 job을 만든다. 실패한 모델 응답을 fixture로 대체하거나 과거 성공 상태를 복원하지 않는다. 단계별/전체 예산이 끝나면 needs_attention에 멈추고 사용자 재시도는 새 run으로 기록한다. 누적 실패/수동 개입을 별도로 유지한다.

### 작업 삭제

1. UI가 대상 작업 이름과 삭제 범위를 보여준다. 사용자가 `DELETE`를 입력하고 별도 저장 기준이 남는다는 설명을 확인한다.
2. 서버가 현재 세션, task 존재, expected_revision, `confirmation="DELETE"`, `acknowledge_saved_rules_retained=true`를 검증한다.
3. 현재 job 취소를 요청하고 task의 원자료/근거/결정/미리보기/팩/결과/export/trace/event와 관련 멱등 응답/캐시를 같은 삭제 계약으로 정리한다.
4. 해당 작업에서 만든 재사용 규칙의 원작업 FK는 해제한다. 원문/실제값을 복제하지 않은 최소 출처 정보와 조건만 남긴다. 규칙 철회는 F06의 별도 사용자 행동이다.
5. 실행 임시 데이터와 앱이 관리하는 캐시를 정리한다. 늦은 worker의 결과 저장은 task 존재성/FK/CAS로 거부한다.
6. 삭제 완료 후 UI 목록으로 이동하고 현재 작업 데이터를 메모리에서 제거한다.

삭제 확인 실패는 어떤 데이터도 변경하지 않는다. 일반 DB를 demo-reset으로 삭제하는 경로는 없다. 이미 삭제된 task의 재시도는 멱등 계약에 따른 비민감 결과만 반환한다. 삭제된 내용이 idempotency 응답에 다시 등장하지 않게 한다.

## 6. 다른 기능과 계약

| 서비스 / API | 입력 | 반환 / 연결 |
| --- | --- | --- |
| `TaskService.ListTasks` / `GET /api/v1/tasks` | cursor, 지원 필터 | 내부 작업 요약과 다음 cursor |

F01~F08은 상태 변경 이벤트를 공통 store에 기록한다. 각 기능이 독자 이벤트 저장소/재시도 상태를 만들지 않는다. F05 다운로드는 F09의 과거 성공 이벤트가 아니라 현재 유효성을 조회한다. F10이 세션/외부 telemetry 금지/저장 권한/debug 설정을 집행한다.

## 7. 하지 않을 것

분산 작업 엔진/다중 서버 장애 복구, 이메일/메신저 진행 알림, 영구 원문 감사 로그, 과거 결과 자동 외부 재전송, OS 백업/기존 다운로드 회수, 조직 전체 로그 분석은 범위 밖이다. 작업 삭제와 재사용 기준 철회를 같은 동작으로 묶지 않는다.

## 9. 확인 필요와 구현 순서

실제 보존 기간/백업/배치 정책은 Q-DEPLOY/Q-POLICY다. 가상 PoC의 기본값은 사용자 삭제까지 원자료/작업, opt-in 본문 24시간이다. 운영 정책이 다르면 spec과 UI 안내를 함께 바꾼다.

구현 순서는 task/job/event 트랜잭션 -> CAS/취소/재시작 정리 -> SSE/재조회 -> history UI -> debug 보존 정리 -> 작업 삭제/규칙 참조 해제 -> 경쟁/복구 검증이다. 변경 영향은 F01~F10 전체의 상태 저장과 QA에 걸치므로 공통 함수를 사용한다.
