# QA와 인수 기준

> 보존한 제품 설계·이전 기록이다. 현재 구현은 TypeScript 서버·클라이언트의 문서 저장·조회만 제공한다. 현재 실행과 API는 [README](../README.md) 및 [api](api.md)를 따른다.

문서 버전: 1.0 · 상태: **실행할 시험의 명세**. 아래 시험은 작성 시점에 제품 코드로 실행하지 않았으며, 통과 목록이 아니다.

## 1. 무엇을 각각 검증하는가

| 검증 층 | 판단할 것 | 판정 주체 |
| --- | --- | --- |
| 계약·상태 | 입력, 공개 결정, 참조, revision, 해시, 권한, 멱등성 | 결정적 자동시험 |
| 의미 정확성 | 승인한 사실·제약 유지, 미확인 사항의 단정 방지, 불필요한 정보 포함 여부 | 사전 기준을 가진 사람. 모델 평가만으로 확정하지 않음 |
| 수신자 효용 | 원문 없이 오류 확인 또는 다음 조사 행동을 할 수 있는가 | 개발에 관여하지 않은 수신자 역할 |
| 제품가치 | 같은 품질과 공개 수준까지 준비하는 사람 수고가 줄어드는가 | 직접 작성·일반 사내 AI·SafeHandoff 비교 |

공개 파일에 금지 표식이 없다는 것만으로 의미 수준의 안전이나 유용성이 입증되지는 않는다. 반대로 미승인 문자열을 무조건 모두 지워 기술 단서를 없앤 결과도 성공이 아니다. 정확한 값·원문이 **명시적으로 승인된 양성 사례**를 반드시 포함한다.

## 2. 시험 모드와 증거

- `unit`: 모델·UI 없이 정책/계산/상태 계약 검증.
- `fixture`: 정해진 모델 응답·지연·오류를 사용하는 통합시험. 실제 LLM 품질 성과로 집계하지 않는다.
- `runtime`: 실제 로컬 서버·DB·등록 checker·runner·격리 환경 검증.
- `live`: 실제 사내 LLM이 분석·작성·검토를 수행한다. 준비된 응답 자동 대체 금지.
- `human`: 공개 기준과 의미 조건으로 평가하거나 독립 수신자가 직접 사용한다.

모든 결과는 `pass`, `fail`, `not_run` 중 하나다. 원인, 실행 환경, 입력 해시, revision, 결과 해시, 사람 개입을 함께 기록한다. timeout·환경 없음·설정 없음은 통과가 아니다. fixture에서 pass한 항목이 live 품질 검증을 대신하지 않는다.

## 3. 인수시험 목록

F 번호는 [기능 파일](features/)의 책임 영역, INV 번호는 [spec.md](spec.md)의 불변조건이다. [acceptance-map.csv](acceptance-map.csv)는 개별 AC→시험 ID, [traceability.csv](traceability.csv)는 시험→기능·불변조건·AC를 연결한다. 여러 기능이 닿는 시험에는 관련 F를 모두 표기한다. 연결표의 `not_run`은 아직 제품 시험을 실행하지 않았다는 뜻이다.

## 5. 의미 평가표

각 결과의 의미 판정은 `present`, `absent`, `incorrect`, `not_applicable`, `uncertain`으로 기록한다. 정확한 문장 일치 대신 아래 질문을 사용한다.

1. 승인한 목적상 필수 사실과 제약이 살아 있는가?
2. 관찰·가설·모름이 구분되어 있는가?
3. 제외한 수치·비율·관계·원인·사업 맥락이 다른 표현으로 돌아오지 않았는가?
4. 승인한 정확한 값과 원문은 필요한 만큼 정확히 남아 있는가?
5. 새로 만든 예시를 실제 관찰값처럼 표현하지 않는가?
6. 수신자가 할 수 있는 다음 행동과 아직 필요한 정보가 명확한가?

판정자가 확신할 수 없으면 pass를 추정하지 않고 uncertain과 이유를 기록한다. 테스트용 canary는 exact scan을 쓰되 의미 평가와 구분한다. 숫자 부분 일치가 다른 공개 버전·합성 길이 등에 우연히 나타났다고 곧바로 누출로 집계하지 않는다.

## 6. 모델 검토 효과를 따로 확인하는 방법

동일 초기 초안에 대해 작성만 / 작성+모델 검토 / 작성+검토+앱 검사를 비교한다. 일부러 심은 오류와 자연 생성 오류를 분리해 남은 오류, 새 오류, 불필요한 삭제, 시간·호출 수를 기록한다. “검토 에이전트가 있으니 정확하다”를 성공 근거로 쓰지 않는다.

## 7. 제품가치 비교의 최소 설계

수동 작성, 같은 사내 모델을 사용한 충분히 준비된 일반 AI 대화, SafeHandoff를 비교한다. 일반 AI에도 같은 업무 지침·제품 문서·이전 공개 기준·기본 변환/검사 도구와 수정 기회를 준다. 제품 전용 UI와 revision 집행을 그대로 복제할 필요는 없다.

첫 사용·동일 조건 재사용·수신자/목적 변경을 구분한다. 같은 원문을 반복 읽는 학습 효과를 줄이기 위해 대응되는 다른 입력을 교차 배정한다. 첫 PoC의 한 사람 실험은 측정 방법 점검이며 일반적인 절감률 근거로 쓰지 않는다. 팀이 성공 수치 기준을 원하면 결과를 보기 전에 정한다.

측정은 최초 기준 설정, 질문 응답, 원문 대조, 수정, 최종 확인까지의 **사람 작업 시간**을 포함한다. 모델 대기·실행 시간은 별도 총 경과 시간으로 기록한다. 팩·checker 준비·유지 비용과 수신자의 추가 질문도 포함한다. 측정하지 않은 값은 null이다.
