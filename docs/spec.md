# 동작 명세

상태: 구현 기준 초안 v1.0 · 2026-10-31. 제품 범위는 [PRD](prd.md), 데이터는 [ERD](ERD.md), 요청 형식은 [API](api.md), 역할별 입력은 [에이전트 흐름](agent-workflow.md)을 따른다. 이 문서의 **해야 한다**는 PoC 인수 조건이다. 구현 완료나 보안 인증을 뜻하지 않는다.

## 1. 공통 언어와 권한

서버의 기본 바인딩은 127.0.0.1이며 사용자가 명시한 wildcard 또는 특정 서버 IP 바인딩도 지원한다. listen 주소와 브라우저 Host를 분리한다. wildcard에서는 서버 인터페이스 IP·loopback을 자동 허용하고 추가 접속 이름은 server.allowed_hosts의 호스트:포트로 지정한다. 모든 요청의 Host를 허용 목록에서 검사하고 Origin은 실제 요청 Host와 비교한다. 이 설정은 사용자 수나 공개 승인 권한을 바꾸지 않는다.

| 용어 | 의미 |
| --- | --- |
| 작업 Task | 목적·상대·공개 범위·원자료·선택·출력을 묶는 한 준비 작업 |
| 원자료 Source version | 받은 바이트를 바꾸지 않고 보관한 불변 입력 판본 |
| 근거 Evidence | 특정 원자료 판본의 정확한 위치와 내용 해시 |
| 후보 Candidate | 외부 설명에 쓸지 판단할 사실·제약·가설·미확인 사항. 아직 공개 허가가 아님 |
| 공개 미리보기 Projection | 특정 표현 수준을 선택했을 때 실제로 드러날 내용 |
| 공개 결정 Decision | 미리보기를 보고 사용자가 허용·제외·보류한 기록 |
| 승인팩 Fact pack | 유효한 결정에서 앱이 추린 작성기용 정보. 원자료 요약 전체가 아님 |
| 초안 Artifact | 문서 구조와 그로부터 만들어진 본문·표·첨부의 한 판본 |
| 최종 확인 Finalize | 현재 파일 바이트를 확인하고 복사·저장을 가능하게 하는 사용자 동작 |
| 저장 기준 Rule | 정해진 조건의 다음 자료에 재적용할 표현 방식. 과거 사실 자체를 기억하는 기능과 구분 |
| 확장 Pack | 제품별 질문·공개 양식·검사·실행 방법을 등록한 묶음 |

### 1.1 첫 PoC의 사용자

한 OS 사용자와 그 사용자의 로컬 브라우저를 지원한다. 이 사용자가 자료를 넣고 공개 수준을 결정한다. 사용자 계정·조직 관리자·팀원 초대·결재선은 만들지 않는다. 실제 회사의 공유 승인권자가 누구인지는 Q-POLICY이며, 앱의 버튼이 회사의 승인 권한을 부여하지 않는다.

신뢰 주체는 앱을 설치한 사용자, OS·내부 모델 운영자, 사전 등록된 확장 관리자다. 모델 응답, 자료 본문, 문서 속 명령, 생성 파일은 신뢰하지 않는 입력으로 처리한다. 같은 사내 모델을 여러 역할에 사용해도 역할별 입력을 새로 구성한다.

## 2. 입력과 범위

### 2.1 작업 범위

`purpose_id`는 `oss_issue`, `vendor_support`, `operations_advice` 중 하나다. `audience`는 `public` 또는 `named_external`이다. 수신자는 등록된 `recipient_id`를 고른다. 첫 카탈로그는 공개 이슈, 가상 공급사 비공개 지원, 가상 외부 운영 자문사다. 수신자 ID의 의미는 불변이며 상대가 달라지면 새 ID를 쓴다. 실제 외부 주소로 전송하지 않으므로 URL 입력이나 발송 자격 증명은 필요 없다.

작업의 `goal_variant`는 `default`, `observations_only`, `ask_for_diagnostics`, `reproduction_evidence`다. OSS는 default/observations_only/reproduction_evidence, B2B는 네 종류, 일반 자료는 default를 지원한다. reproduction_evidence는 해당 제품의 등록된 실행 팩이 있어야 선택할 수 있다. default는 관찰 자료로 문의를 준비하는 목표이며 재현은 선행 조건이 아니다. ask_for_diagnostics는 필요한 추가 진단 정보를 묻는 목표다. 목표 축소도 의미 있는 변경이므로 goal_variant 변경은 revision 증가·재분석·공개 결정 재확인으로 처리한다.

공개 선택의 scope는 `project_id + purpose_id + goal_variant + recipient_id + audience + skill_set_hash`다. 저장 기준은 여기에 `schema_id + schema_version + source_slot + selector + transform_id/version`도 일치해야 한다. `output_language` 변경은 재작성·재검토 대상이지만 공개 허용의 의미가 유지되는 한 같은 결정이 사용될 수 있다.

내부 작업 이름·목적 자유 메모·원본 파일명은 비공개다. 외부 본문의 목적 설명은 등록된 공개 양식에서 가져온다. 다른 회사 맥락을 넣으려면 후보와 공개 결정을 만든다.

### 2.2 파일 처리

지원: UTF-8 `txt`, `log`, `md`, `csv`, `json`과 붙여넣기. 붙여넣기도 하나의 원자료 판본으로 저장한다. 실행 파일, ZIP 업로드, PDF·DOCX·이미지·OCR는 P0/P1 범위 밖이다. 파일 확장자와 실제 형식 검증을 함께 한다. 입력을 URL로 받아 서버가 임의 다운로드하는 기능은 없다.

기본 한도는 10개 파일, 파일당 256 KiB, 작업 원자료 합계 1 MiB다. 업로드 한 배치는 전부 성공하거나 전부 실패하고 revision은 한 번 증가한다. 동일 파일명은 내부 표시용이므로 중복될 수 있으나 `source_id`로 구분한다. 같은 내용 재첨부는 자동 공개나 자동 대체가 아니다. 사용자가 교체 대상을 지정해야 이전 슬롯과 연결한다.

원본 UTF-8 바이트와 해시는 그대로 보관한다. 줄바꿈·Unicode를 조용히 정규화하지 않는다. CSV 파서는 UTF-8 BOM을 허용하되 원본은 보존한다. CSV 중복 헤더, 다른 열 수, JSON 중복 키·후행 JSON·잘못된 UTF-8는 거부한다. 문자열을 숫자로 임의 변환하지 않는다. CSV 수치 필드는 등록 스키마의 엄격한 십진 정수 파서를 사용한다. requests_v1의 count는 0–9007199254740991이며 지수 등 계산 결과는 필요한 경우 typed decimal string으로 전달한다.

파일을 업로드할 수 있다는 것과 모델이 전체를 분석할 수 있다는 것은 별개다. 모델 입력 한도를 초과하면 분석 완료로 표시하지 않는다. 사용자가 자료를 줄이거나 선택을 좁혀야 한다. 첫 버전은 조용한 일부 분석·자동 문맥 압축·생략을 하지 않는다.

### 2.3 근거

앱이 근거 ID를 먼저 발급한다. 모델에게 바이트 위치를 계산시키지 않는다.

| 형식 | 위치 표현 | 검증 |
| --- | --- | --- |
| 텍스트 | UTF-8 바이트 반열린 범위 `[start,end)` | 범위·문자 경계·선택 바이트 해시 |
| CSV | 데이터 행 0 기반 번호 + 열 이름 | 등록 스키마, 행 존재, 셀 값 해시 |
| JSON | JSON Pointer | 문서 판본·경로·값의 정규 직렬화 해시 |

근거는 `source_version_id`, `source_sha256`, `locator`, `evidence_sha256`를 함께 가진다. 표시용 줄 번호나 비슷한 문장 검색은 권한 참조를 대체하지 못한다. 원문 인용은 실제 바이트 범위를 추가로 지정한다.

## 3. 후보와 공개 결정

### 3.1 후보 분류와 필요한 정보

`kind`는 `observation / constraint / hypothesis / unknown`, `uncertainty`는 `observed / reported / inferred / unknown`이다. `relevance`는 `required / optional`이고 필요 이유를 보여준다. `required`는 현재 문의 목적에 필요한 단서라는 뜻이며 공개 의무가 아니다. 사용자는 제외하고 문의 범위를 줄일 수 있다.

서로 모순되는 자료는 `conflict_group`으로 함께 표시한다. 한쪽을 조용히 정답으로 채택하지 않는다. 사실을 수정하려면 근거와 후보를 수정·추가하고 필요한 결정을 다시 받는다. 수동 후보도 `origin=human`으로 같은 흐름을 거친다. 모델 장애로 수동 경로에 들어가도 검토 기준은 유지한다.

등록 공개 양식은 목적·goal별 필요한 정보 분류(`need_keys`)를 정한다. 기본 분류는 environment, observation, observed_sequence, expectation, uncertainty, question, diagnostic_question, process, constraints, reproduction_result다. 정확한 조합은 domain-contract의 template_needs다. 모델의 relevance와 need_keys는 제안이며 실제로 필수 의미를 충족하는지는 작성 중·최종 의미 검토에서 확인한다.
같은 분류의 승인 후보가 이미 충분하면 중복 후보 전부를 공개할 필요는 없다. 알려지지 않은 환경은 그 사실을 unknown으로 승인해 설명할 수 있다. 재현 결과는 finalization 단계의 필수 정보이며 실행 전 선택 게이트에서 제외한다. reproduction_evidence의 재현 성공 조건은 unknown으로 충족할 수 없다.

수동 후보 추가는 새 candidate_set을 만든다. 기존 유효 후보를 검증 후 새 ID로 복제하고 새 후보를 추가하며, user_note가 있으면 같은 트랜잭션에서 source/evidence도 만든다. revision은 한 번 증가하고 needs_decisions가 된다. 이전 후보의 결정은 자동 이전하지 않고 이전 선택을 참고로 보여준다. 이 경로는 모델 재분석 없이도 수동 복구할 수 있어야 한다. 일반 원자료 교체·추가의 needs_analysis와 구분한다.

### 3.2 허용·제외·보류

`disposition=allow`는 미리보기에 표시한 정보만 허용한다. `exclude`는 이번 결과에서 사용하지 않는다. `defer`는 아직 결정하지 않았음을 뜻한다. 신규 후보는 자동 허용하지 않는다. 이미 사용자가 저장한 유효한 변환 기준의 재적용은 출처를 표시하고 새 결정으로 기록한다.

결정이 없는 optional 후보는 사용하지 않고 진행할 수 있다. 명시적으로 보류한 후보와 필요한 미결정 후보는 최종 확정을 막는다. 보류된 후보를 빼고 임시 초안을 만들 수 있으나 `draft`와 미완료 표시를 유지한다. 공개할 내용이 전혀 없으면 빈 문서로 성공 처리하지 않는다.

### 3.3 세 가지 허용을 구분

| 허용 종류 | 예 | 결합할 범위 |
| --- | --- | --- |
| 의미와 표현 수준 | 요청량이 증가했다는 사실, 방향 표 | 승인한 문장·관계·변환 결과와 scope |
| 정확한 값 | 이번 문의의 추적 ID, 제품 버전, 요청 건수 | 원자료 판본·근거·해당 실제 값·scope |
| 원문 구간 | 오류 코드가 있는 1줄의 승인된 렌더링 | 원자료 판본/해시·범위·숨김 범위·최종 인용 바이트 해시·scope |

정확한 값이 공식 공개 값처럼 보여도 첫 PoC에서는 현재 자료에서 사용 여부를 결정한다. 정확한 값과 원문 허용은 `reusable=false`다. hidden_ranges는 원자료 기준 절대 UTF-8 byte 범위이며 발췌 범위 내 정렬·비중첩·문자 경계를 만족해야 한다. 고정 `[가림]` 바이트로 치환하고 잘못된 범위는 보정하지 않고 거부한다. 승인 원문은 앱의 `excerpt_ref`로 삽입하고 작성기에게 주변 원문을 넘기지 않는다.

| B 추이만 보이게 나머지 마스킹 | `derived_table` / `series_direction_only.v1` | 첫 번째: 기준, 두 번째: 증가, 세 번째: 증가 | 건수·비율·날짜·실제 간격·단위 |
| C 요청 정보 마스킹 | `selected_fields` / `select_fields.v1` | 사용자가 남길 열과 그 실제 값만으로 만든 새 표 | 선택하지 않은 열·주변 원문·다음 자료의 값 |
| D 기타 (직접 입력) | 해석 후 등록 표현과 변환으로 고정 | 예: 첫 관찰을 100으로 한 `100,141,212` | 자유 지시문을 곧바로 실행하거나 권한으로 쓰지 않음 |

B와 C의 ‘마스킹’은 사용자가 고르는 공개 수준의 이름이다. 실행은 승인한 정보로 새 표를 생성한다. 원자료 파일 전체를 일부 수정해 그대로 내보내는 모드가 아니다. C가 실제 값을 남기면 해당 정확값 허용을 결정에 기록한다.

`series_fact_summary.v1`은 인접값을 모두 비교한다. 모두 엄격히 증가하면 위 문장, 모두 엄격히 감소하면 감소 문장, 모두 같으면 변화 없음이다. 증가와 감소가 둘 다 있을 때만 ‘관찰된 구간에서 요청량이 오르내렸습니다.’를 쓴다. 증가와 동률만 있으면 ‘요청량이 줄어들지는 않았고, 증가한 구간이 있습니다.’, 감소와 동률만 있으면 그 반대 방향 문장을 미리보기로 제시한다. 한 관찰만 있으면 변화 사실을 만들지 않고 `INSUFFICIENT_OBSERVATIONS`를 반환한다. 후보와 맞지 않는 요약은 새 미리보기로 확인한다.

지수 변환은 첫 값 대비 백분율이며 공개 정보에 상대 규모가 포함됨을 표시한다. `decimal_places=0`을 기본으로 하고 0–4만 허용한다. 정확한 유리수 계산 후 HALF_UP 반올림한다. 첫 값이 0이면 `INDEX_BASELINE_ZERO`, 음수·결측·형식 오류는 `INVALID_SERIES`다. 값을 채우거나 행을 조용히 버리지 않는다. `820,780,1740`은 감소·증가이며 계속 증가했다고 쓰지 않는다.

### 3.5 미리보기와 적용의 원자성

1. `CreatePreview`가 현재 revision·후보·표현의 실제 투영을 계산한다. 공개될 문장·표·원문 구간을 보여준다.
2. 서버에 `preview_id`, 입력 revision, 표현 JSON, 투영 바이트·해시를 저장한다. 미리보기 생성은 공개 결정이 아니며 revision을 올리지 않는다.
3. 사용자는 허용할 미리보기 또는 제외·보류를 한 배치로 적용한다.
4. 서버는 같은 revision인지 확인하고 모든 allow 항목을 다시 계산한다. 저장된 해시·요청 해시·재계산 해시가 같아야 한다.
5. 모든 항목이 유효할 때만 불변 결정 레코드와 현재 포인터를 함께 저장하고 revision을 한 번 올린다. 하나라도 실패하면 전부 저장하지 않는다.

서로 다른 카드의 미리보기를 revision N에서 만들었다면 한 배치로 승인할 수 있다. 먼저 한 카드를 N+1로 저장한 뒤 다른 N 미리보기를 승인하면 409를 반환하고 미리보기를 갱신한다. 브라우저가 revision 숫자만 고쳐 보내는 것은 허용하지 않는다.

결정 변경은 `supersedes_id`가 있는 새 레코드다. 기존 레코드를 덮어쓰지 않는다. 현재 결정이 철회·만료되면 과거 허용으로 돌아가지 않는다. 만료 시각 null은 시간 제한 없음이며 범위·원자료 판본·철회 조건은 계속 적용한다.

### 3.6 직접 입력과 직접 편집

D 입력은 `supported / ambiguous / unsupported`로 해석한다. 지원되는 변환 ID·검증된 매개변수·계산된 미리보기를 보여준 뒤 사용자가 적용한다. 애매하면 질문하고, 미지원이면 가능한 선택을 제시한다. 코드·SQL·임의 정규식은 실행하지 않는다.

문장 직접 편집은 내부 새 초안을 만든다. 새로운 사실·수치·원문이 들어오면 후보+공개결정으로 돌아간다. 편집 API는 fact ID를 임의로 만들어 승인하지 못한다. 알려진 참조와 형식은 기계적으로 검사하고 의미 변화는 모델 또는 사람이 검토한다. 시스템이 모든 의미 추가를 자동 식별한다고 주장하지 않는다.

## 4. 작성·검토·파일 생성

### 4.1 승인팩

승인팩은 현재 유효한 결정에서 앱이 결정적으로 구성한다. `facts`, `required_fact_ids`, `tables`, `excerpt_slots`, `asset_slots`, 허용된 정형 도구 결과, 공개 양식만 포함한다. 원자료 이름·내부 제목·미승인 후보·원자료 위치·결정 이유·모델 분석 대화는 내부 매핑에 남긴다. 상세 계약은 [에이전트 흐름](agent-workflow.md)을 따른다.

요약 문장 하나를 허용했다고 관련 표나 정확한 수치까지 허용된 것은 아니다. 표·원문·도구 결과는 별도 허용 항목에 연결한다. 공개 정보는 있어도 현재 목적을 설명할 수 없으면 질문 또는 문의 범위 축소를 제안한다.

### 4.2 역할과 반복

분석 → 선택 → 승인팩 → 작성 → 작성 중 검토 → 필요한 수정 또는 추가 선택 → 파일 생성 → 후처리 및 예외 반영 등 → 실제 파일 검토 → 사용자 확인 순서다. 작성 중 검토가 필수이며 마지막 검사만으로 대체하지 않는다. 한 사내 모델을 순차 사용해도 된다.

검토가 추가 정보를 원하면 후보를 질문으로 보내고 기다린다. 작성기에는 `reason_code`, 현재 승인 fact ID, 삭제 대상 block ID 등 검증된 지시만 전달한다. 원문을 포함할 수 있는 자유 설명을 전달하지 않는다. 원문 분석자와 검토자의 대화 세션을 작성 역할에 재사용하지 않는다.

### 4.3 모델 실패

기본 모델 호출은 120초 제한, 단계당 최대 2회, 자동 수정 최대 2회, run 전체 최대 12회다. 인증·설정 오류와 명확한 문맥 초과는 즉시 중단한다. 일시적 네트워크·429·5xx는 최대 5초 대기 후 한 번 재시도한다. 응답이 잘렸으면 일부를 성공으로 쓰지 않는다.

작은 모델이 구조 출력을 못 하면 strict JSON 오류를 표시하고 수동 후보·수동 문서·사람 의미검토 경로를 제공한다. 입력이 원자료라는 사실이나 공개 결정 조건은 변하지 않는다. `mode=human`과 이유를 기록하며 모델 검토 성공으로 세지 않는다.

### 4.4 두 종류 검사

기계적 필수 검사: revision, 객체 소속, 현재 결정, 근거, 원문 grant, 참조 슬롯, 파일명/형식/해시, 등록 asset, 도구 결과 범위, 미결정 여부. 실패하면 최종 확인을 막는다.

의미 검토: 승인된 의미만 있는지, 누락·왜곡·근거 없는 원인·미확인 사항 삭제가 없는지. 모델 검토를 완료할 수 없으면 사용자가 실제 대상과 미해결 항목을 확인해 대체할 수 있다. 사람 검토가 새로운 공개 허용이나 필수 검사 오류 면제는 아니다.

IP·토큰·URL·내부 경로 검사기는 보조 finding을 만든다. 허용된 정확값·원문·공개 asset·문맥 예외에 연결해 위치별로 해소한다. ‘검사 통과’는 모든 정보가 안전하다는 증명이 아니다. UI 문구는 ‘현재 선택 기준 검사 완료’다. 모든 보안 finding은 severity와 무관하게 해소해야 한다. severity는 UI 우선순위이며 비보안 안내는 finding 대신 event로 둔다.

### 4.5 결과물

P0 결과는 새 Markdown 본문, 선택한 CSV·JSON·승인 인용, manifest, ZIP이다. 파일명은 공개 양식의 allowlist에서 정하고 내부 이름을 자동 사용하지 않는다. 입력 파일 전체·작업 DB·trace·근거 기록·평가 정답표를 내보내지 않는다.

DocAST는 heading, paragraph, list, table_ref, excerpt_ref, asset_ref만 지원한다. 임의 HTML·iframe·외부 이미지·직접 파일 경로·실행 URL은 금지한다. 링크는 등록된 공개 asset으로 다룬다. 표·원문 슬롯·첨부 설명을 실제 파일로 렌더링한 뒤 검토한다.

CSV는 LF, UTF-8로 출력한다. 숫자·문자열을 구분한다. 문자열의 선행 공백을 제외한 첫 문자가 `=,+,-,@`이거나 원래 시작에 TAB/CR/LF가 있으면 앞에 apostrophe를 붙이고 그 결과를 미리 보여준다. 실제 숫자형 음수는 문자열 위험 처리와 구분한다. 이 변환은 대상 프로그램 전반에 대한 보안 보증이 아니다.

파일 집합 해시는 manifest를 포함한 정렬된 `path,size,sha256` 목록의 공통 직렬화 해시다. 공개 manifest는 payload만 열거하며 자기 자신과 ZIP은 넣지 않는다. ZIP 해시는 따로 저장한다. 경로 정렬·고정 수정 시각·고정 권한·빈 주석을 사용한다. 작업 디렉터리 전체를 압축하지 않는다.

## 5. 상태와 동시성

공통 enum의 기계 판독 원본은 [domain-contract.json](../contracts/domain-contract.json)이다.

| 객체 | 상태 |
| --- | --- |
| task.phase | needs_analysis, needs_decisions, ready_to_generate, processing, needs_attention, ready_to_finalize, finalized |
| artifact.status | draft, checking, blocked, ready, finalized, stale |
| job.status | queued, running, succeeded, failed, cancelled, stale |
| review.result | pass, needs_changes, needs_decision, error |
| reproduction.status | not_requested, not_run, running, reproduced, not_reproduced, inconclusive, error |

`revision`은 1부터 시작하고 입력·사용자 선택의 판본을 의미한다. `artifact_version`은 같은 revision에서 자동으로 작성·수정한 출력 판본이다. `job_id`는 비동기 실행 한 번이다. 셋을 하나의 번호로 합치지 않는다.

| 사건 | revision / 결과 | 다음 상태 |
| --- | --- | --- |
| 작업 생성 | revision=1, 결과 없음 | needs_analysis |
| 원자료 추가·교체·제외 / 목적·goal_variant 변경 | +1, 이전 결과 stale | needs_analysis |
| 분석 성공 | 현재 candidate_set 교체, 일치하는 저장 기준 재계산 | 미결정이 있으면 needs_decisions, 없으면 ready_to_generate |
| 수동 후보·user_note 추가 | +1, 새 candidate_set, 이전 결정 자동 이전 없음 | needs_decisions |
| 결정 배치 성공 | +1, 기존 결과 stale | 모두 해소하면 ready_to_generate, 아니면 needs_decisions |
| 상대·공개범위 변경 | +1, 이전 허용 새 scope에 불일치 | needs_decisions; 목적도 바뀌면 needs_analysis |
| 작성 시작 | 입력 스냅샷·current_job_id 설정 | processing |
| 검토 추가 질문 | 초안 보존, 새 권한 없음 | needs_decisions |
| 자동 수정·렌더링 | 같은 revision의 artifact_version 증가 | processing |
| 실제 파일과 검토 완료 | 현재 artifact.status=ready | ready_to_finalize |
| 사용자 최종 확인 | revision 유지, 불변 export 생성 | finalized |
| 내부 제목·출력 언어 변경 | +1, 기존 결과 stale; source/scope가 같은 결정은 재검증 후 유지 | ready_to_generate 또는 needs_decisions |
| ready/finalized에서 재작성·편집 | +1, 이전 결과 stale | processing 또는 needs_attention |
| 내부 제목·출력 언어 변경 | +1, 이전 결과 stale; source/scope가 같은 결정은 재검증 후 유지 | ready_to_generate 또는 needs_decisions |
| 기준 철회·만료 / 허용 철회 | 영향 작업 +1, 현재 export 무효 | needs_decisions |
| 오류·예산 소진 | 실패 원인·중간 결과 보존 | needs_attention |
| 재시작 시 queued/running | job=failed, code=INTERRUPTED | needs_attention |

### 5.1 결과 적용 조건

비동기 결과는 아래를 짧은 트랜잭션에서 모두 확인한 뒤 적용한다.

```text
task.revision == job.input_revision
task.current_job_id == job.id
job.cancel_requested == false
snapshot의 source / scope / 결정 / 기준 / 확장 판본이 여전히 유효
검토이면 target_hash == 현재 검사 대상 hash
```

불일치는 `stale` 또는 `cancelled`다. 현재 포인터를 바꾸지 않는다. 같은 revision의 이전 job도 current_job_id로 차단한다. 취소 실패는 이 조건을 약하게 만들지 않는다. 취소는 revision을 올리지 않고 해당 job을 취소 표시한다. 다음 실행은 새 job ID를 쓴다. 사용자 선택 저장은 이전 모델 응답을 기다리지 않는다.

작업당 실행은 한 개, 모델 전체 동시성은 기본 1이다. 새 작업 중복 시작은 `JOB_ALREADY_RUNNING`이다. 선택 변경은 진행 중 작업을 무효화하고 취소 요청한다. 취소를 지원하지 않는 모델 API도 결과 적용을 막을 수 있어야 한다. 모델·도구 실행 중 DB 트랜잭션을 열어 두지 않는다.

새 분석 결과를 채택할 때 snapshot의 유효한 저장 기준을 새 자료에 계산해 파생 결정을 같은 트랜잭션에 만들 수 있다. 이 자동 산출은 현재 revision을 유지하며 applied_rule_id/version을 기록한다. 사용자가 중간에 재적용을 요청하면 새 revision이다. 규칙이 겹쳐 서로 다른 결과를 허용하면 자동 우선순위를 만들지 않고 질문한다.

task_snapshots는 revision 생성 당시 입력·선택·규칙을 보관하며 자동 산출로 수정하지 않는다. 각 job은 실행 시작 시 현재 결정과 규칙을 다시 검증한 effective snapshot을 jobs.snapshot_json에 따로 저장한다. compose는 분석 전의 task snapshot만 복사해서 권한을 판단하지 않는다. fact_pack은 같은 revision에서도 새 도구 결과에 따라 별도 불변 ID를 가질 수 있다.

### 5.2 만료와 철회

만료는 실행 시작·결과 적용·최종 확인·다운로드에서 현재 시각으로 재검사한다. 만료 처리 시 영향 revision을 한 번만 증가시킨다. 이미 stale로 표시한 같은 무효화 사건을 반복 조회한다고 계속 증가시키지 않는다. 기준 버전 업데이트는 기존 결정을 조용히 바꾸지 않는다. 적용 또는 철회 동작을 명시한다.

## 6. 최종 확인과 파일 반환

최종 확인은 서버의 현재 revision, artifact ID, artifact_set_hash, 결정/기준 유효성, 필수 검사, 의미 검토를 다시 검사한다. 검토 화면과 다른 바이트·파일 목록이면 409다. 미결정·원문 승인 누락·필수 검사 실패는 422로 이유를 반환한다. default/observations_only/ask_for_diagnostics의 재현 `not_run/no_environment`는 관찰 기반 문의 완료를 막지 않는다. reproduction_evidence는 reproduced여야 목표 완료로 확정할 수 있다. 그 목표를 수행할 수 없으면 사용자가 observations_only로 바꾸고 재분석·결정을 거친다. 실패 결과는 내부 이력에 남긴다.

확정 API는 이미 만들어 검사한 ZIP과 파일을 연결한다. 확정 후 모델을 부르거나 파일을 재생성하지 않는다. 같은 멱등 요청은 같은 export ID를 반환한다. 다운로드 때도 현재 승인과 해시를 확인하므로 이후 선택 변경·철회가 있으면 `EXPORT_INVALIDATED`다. 이전 결과는 내부 이력에서 볼 수 있지만 공식 복사·다운로드 동작은 제공하지 않는다. 이미 사용자가 받은 파일을 회수할 수는 없다.

외부 공유는 사용자가 별도로 한다. 첫 PoC에는 GitHub issue 생성, 이메일, 티켓 자동 제출을 구현하지 않는다. 향후 연결해도 수신처·공개 범위·동일 파일 확인을 새 동작에 결합한다.

## 7. 재사용과 확장

기본 규칙은 등록된 `requests_v1` 자료의 count에 대한 사실 요약·방향·지수 변환이다. 새 자료에서 다시 계산한 실제 결과를 보여주고 적용 근거를 표시한다. 자유 문서의 유사한 내용은 제안만 한다. 정확값·원문·과거 결과물을 권한으로 복사하지 않는다. 상세는 [F06](features/06-decision-reuse.md).

제품 지침과 검사기 설치는 운영자 설정이다. 실행 중 자료나 모델이 설치하지 않는다. 공개 양식과 내부 분석/검토 지침을 분리한다. 맥락 예외는 현재 파일의 지정 finding에만 적용된다. 상세는 [확장](extensions.md), [F07](features/07-domain-extensions.md).

재현은 별도 상태로 관리한다. 준비된 고정 대상·판정기로 새 입력을 실행한다. 실행 전에 target·합성 input·공개할 결과 schema/필드를 선택한다. 실행 후에는 그 범위의 정형 결과만 승인팩에 투영한다. 아직 없는 reproduction_result 때문에 실행 자체를 막지 않는다. 결과 자유문장·stderr·원자료의 새 정확값은 이 허용에 따라오지 않는다. 실제 결과 파일은 생성 뒤 현재 hash에 대해 검토·최종 확인한다. 실패하면 환경·대상·가설·부족한 정보 중 무엇을 확인할지 제안한다. 무조건 정보를 더 공개하게 하지 않는다. 상세는 [F08](features/08-reproduction.md).

## 8. 보존·삭제·기록

원자료·초안·선택·결과는 기본적으로 사용자가 작업을 삭제할 때까지 내부 DB에 보관한다. 입력에서 제외하는 것과 작업 삭제는 다르다. 작업 삭제는 현재 실행 취소, 파생 데이터·export·내부 trace 삭제를 포함한다. 이미 저장한 재사용 기준은 원자료를 포함하지 않으며 계속 남길 수 있음을 삭제 화면에 알린다. 기준은 별도로 철회한다.

원시 모델 요청/응답 저장은 기본 off다. 디버그에서 명시적으로 켠 경우 내부 전용, 24시간 후 정리하며 작업 삭제 때 즉시 삭제한다. 모델명·모드·호출시간·오류코드 등 내용 없는 메타데이터는 작업 이력에 남긴다. 앱 삭제는 OS 백업·이미 다운로드한 파일·사내 모델의 별도 보관까지 지우는 기능이 아니다.

SSE와 일반 앱 로그에는 원문·모델 토큰·자격 증명·trace body를 넣지 않는다. 진행 정보만 보내고 필요한 결과는 인증된 객체 API로 가져온다. 오류는 안전한 코드와 복구 행동으로 표시한다.

## 9. 변경 관리

제품 범위는 PRD, 상태·허용 규칙은 이 문서, 데이터/DTO는 ERD/API/contracts를 같은 PR에서 변경한다. 기능 문서만 수정해 예외를 만들지 않는다. 요구사항 변경 시 관련 feature와 QA ID를 추적한다. 자세한 순서는 [작업 계획](plan.md).

기존 문서의 설명·예시도 이 명세와 API/contracts에 맞춘다. 자동 제출·특정 모델/GPU를 요구하지 않으며, 재현 필수 여부는 goal_variant로 판단한다. 기본 수치 예시는 820/1160/1740, 지수는 정수 100/141/212이며 소수 자릿수 기본값은 0이다. 기존 한국어 설계·API·시연 안내는 이 기준의 요약으로 유지한다. 현재 코드가 다른 부분은 구현 공백으로 검증보고서에 기록하고, 문서만으로 구현됐다고 표시하지 않는다.
