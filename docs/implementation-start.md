# 구현 에이전트에게 전달할 시작 지시

이 문서와 저장소의 문서 묶음을 함께 전달한다. **현재 파일들은 명세·가상 입력·평가 틀이다. 실행 앱이 이미 구현됐다는 뜻이 아니다.**

## 1. 그대로 전달할 작업 지시

> SafeHandoff PoC를 구현하라. 목적은 사용자가 회사 자료를 외부에 공유하기 전에, 목적에 맞는 공개 수준을 선택하고 공유용 자료를 준비하는 수고를 줄이는 것이다.
>
> README의 읽는 순서에 따라 AGENTS.md, intent.md, docs/prd.md, docs/spec.md, docs/ERD.md, docs/IA.md, docs/uj.md, docs/plan.md, docs/qa.md, docs/test-data.md와 맡은 docs/features 파일을 먼저 읽어라. intent.md는 명시적으로 승인된 변경만 적용하고, 그 범위 안의 일반 구현과 문서 정합성 수정은 계속 진행하라. 공통 계약과 feature 명세가 다르면 기능만 임의로 해석하지 말고 상위 문서를 포함해 정합성을 고쳐라. 사용자 최신 결정이 우선이다.
>
> 기본 구현은 Go 단일 애플리케이션, SQLite, 서버 렌더링 HTML과 순수 JavaScript다. 사내 LLM은 교체 가능한 Provider로 연결하며 일반 텍스트 응답만 필수로 한다. 특정 모델·GPU·VRAM·서빙 런타임을 요구하지 않는다. 모델/라이브러리 버전은 실제 사용 가능 여부를 확인하고 lock 파일에 고정한다.
>
> 작업은 기능 설계 확인 → 계약·예시 환경 → 상태·공개 결정·판본 → fixture 수직 흐름 → 실제 모델 → 확장 → 인수시험 순서로 진행하라. 모델 연결이 없으면 fixture로 상태·UI·파일 구현을 계속하되 live 완료라고 표시하지 마라. live 장애 시 fixture로 자동 대체하지 마라.
>
> 원문은 분석·검토 영역에 두고, 작성기는 앱이 현재 결정으로 구성한 공개 정보만 받게 하라. 전체 새 작성이 기본이다. 정확한 값이나 원문을 사용할 때는 해당 자료 판본과 공개 미리보기의 승인을 확인하라. 업로드, 편집, 모델 제안, 최종 확인을 새로운 공개 허가로 취급하지 마라.
>
> 작성 중 검토를 포함하고, 추가 공개가 필요하면 사용자의 선택 단계로 돌아가라. 검토기가 읽은 원문 설명이나 도구 stderr를 writer 수정 프롬프트로 전달하지 마라. 모델 실패는 정해진 예산 안에서 처리하고, 사람 의미 검토와 서버 hard gate를 분리하라.
>
> 모든 변경·늦은 응답·취소·중복 요청·확정·다운로드는 revision과 현재 객체/해시 계약을 지켜라. 최종 확인한 실제 파일 바이트를 그대로 복사·다운로드하게 하라. 자동 외부 전송은 구현하지 마라.
>
> 세 가상 사례를 사용하되 evaluation/expected와 fixtures/reference-pack/recipient는 생성 앱·모델·도구 입력에서 제외하라. toy 재현과 맥락 예외는 사전 등록한 프로그램만 실행하라. 새 입력이 목표 오류를 재현하지 않으면 결과를 사실대로 표시하고 공개 범위를 자동 확대하지 마라.
>
> 실제 정보가 없어 결정할 수 없는 항목만 확인 필요로 남겨라. 그 밖의 PoC 기본값은 decisions.md의 D 결정을 따른다. 작업 결과에는 실행 방법, 완성 범위, 시험별 pass/fail/not_run, 실제 모델·사람 개입, 공개 파일 예시, 미완료 항목을 보고하라. 측정하지 않은 개선율이나 보안 보장은 쓰지 마라.

## 2. 첫 작업 세션에서 할 일

1. 기존 저장소가 있으면 현재 파일과 변경 사항을 확인하고 사용자 작업을 보존한다. 이 패키지 밖의 저장소 규칙도 읽는다.
2. 맡은 기능 파일에 쓰인 PRD·INV·AC를 읽고, 맞닿는 DTO·API를 확인한다.
3. 개발자가 해석해야 할 공백을 찾아 `decisions.md`의 D/Q 및 상위 문서와 함께 기록한다. “확인 필요”를 편리한 기본값의 대체로 남발하지 않는다.
4. 전체 테스트 환경과 생성 앱의 접근 경로를 분리한다. 평가 정답을 프롬프트에 넣지 않는다.
5. 실제 Go 버전과 의존성을 고정하고 최소 실행·테스트를 준비한다. 패키지 다운로드는 준비 단계에서 끝내고 runtime 외부 인터넷 접근과 구분한다.
6. DB·도메인 로직을 구현한 뒤 fixture API로 한 사례를 끝까지 통과시킨다.
7. 다음 단계로 넘어가기 전에 해당 기능의 AC와 QA 번호를 기록한다.

## 3. 구현 저장소가 제공할 명령

아래는 **구현해야 할 인터페이스**다. 이 문서 패키지에서 이미 실행 가능한 명령이 아니다.

| 명령 | 책임과 성공 조건 |
| --- | --- |
| `just setup` | 고정 Go 모듈·필수 로컬 자원 준비. 사내 모델 설치나 GPU 설정은 강제하지 않음 |
| `just build` | 서버, fixture 생성기, evaluator, 등록 checker 빌드 |
| `just fixtures` | 고정 seed의 가상 입력과 공개 예시 검증·생성. 평가 정답은 별도 관리 |
| `just check` | 사내 endpoint·Docker 없이 가능한 도메인·API·fixture 시험 |
| `just run-fixture` | 전용 개발 DB와 fixture 표시로 로컬 서버 실행 |
| `just run` | 설정된 사내 LLM 연결, 실제 endpoint 없으면 명확한 설정 오류 |
| `just prepare-runners` | toy 대상·checker·실행 이미지를 사전 빌드하고 digest 기록 |
| `just test-extensions` | 실제 등록 process checker와 고정 재현 환경을 실행 |
| `just test-live` | 가상 입력으로 실제 사내 모델의 역할과 실패 처리 검증 |
| `just eval` | 실제 내보낸 결과와 별도 평가 정답을 비교해 기록 생성 |
| `just seed-demo` | 전용 demo DB에 자료만 입력. 공개 결정은 미승인 상태 |
| `just demo-reset` | 전용 demo 데이터만 정리. 일반 사용자 DB 경로는 거부 |
| `just start` / `just start-fixture` | 빌드 후 live/fixture 서버를 백그라운드로 시작, 중복 실행 확인 |
| `just stop` / `just restart` / `just restart-fixture` | 관리 중인 PID의 소유 확인 후 정상 종료·재시작. DB 유지 |
| `just status` / `just logs` / `just logs-follow` | .local/run의 상태·최근 로그·실시간 로그 조회 |
| `just test-server` | 임시 서버로 생명주기·실패 정리·PID 재사용 보호·포트 충돌 시험 |

시험 CLI 종료 코드는 `0=선택한 필수 시험 모두 통과`, `1=시험 실패`, `2=필수 환경 없음/미수행`이다. 개별 시험 상태는 보고서에 모두 남긴다. 환경이 없다고 해당 시험을 조용히 생략하고 0으로 종료하지 않는다.

## 4. 실행 설정과 비밀 값

Provider 설정에는 API root, model ID, 인증 환경 변수 이름, timeout·문맥·출력 예산·지원 매개변수를 둔다. 실제 값은 운영자가 제공한다. 앱과 live evaluator는 현재 디렉터리의 선택적 `.env`를 자동으로 읽고 이미 export된 환경 변수를 우선한다. 인증 키·원문·상세 trace를 Git·외부 telemetry에 넣지 않는다. 연결 확인은 비민감한 짧은 요청으로 한다.

기본 바인딩은 `127.0.0.1`이다. 사용자가 명시한 wildcard/서버 IP 바인딩을 지원하고 서버 인터페이스 IP 또는 server.allowed_hosts에 등록한 호스트:포트로 접속한다. Origin은 실제 요청 Host와 일치해야 한다. 시작 시 출력한 5분 일회용 토큰으로 로컬 세션을 열고 세션·CSRF·Host·Origin 검사를 사용한다. 실제 회사 배포를 로컬 PoC의 검증된 보안 범위처럼 확대 설명하지 않는다.

원문·작업 이력은 사용자 삭제까지 유지한다. 상세 모델 request/response 저장은 기본 꺼짐이며 명시한 debug 실행에서만 최대 24시간 보존한다. 평가자가 writer 요청을 검사할 때도 가상 자료를 사용하고 검사 후 정리한다. 작업 삭제 시 해당 원문·trace·결과·내보내기를 제거한다.

## 5. 구현 중 허용되는 조정

같은 기능·상태·경계·계약·인수기준을 유지하는 내부 함수 분리와 코드 정리는 담당자가 결정할 수 있다. 라이브러리 교체로 API나 패키지 구조가 달라지면 계약과 테스트를 함께 수정한다. 새로운 공개 수준, 수신자 범위, 자동 승인, 외부 네트워크, 임의 코드 실행은 구현 편의로 추가하지 않는다.

실제 endpoint·권한·OSS 라이선스·배포 운영 정책은 사실을 확인해야 하는 Q다. API 연결이 미정이어도 fixture·도메인·화면·toy 입력의 개발은 진행한다. 확인할 수 없는 실제 조직 정책을 가정해 “승인 완료”로 기록하지 않는다.

## 6. 최종 보고에 포함할 것

- 실행 명령과 필요한 실제 설정, 개발·runtime 환경의 구분.
- P0와 P1 기능별 완료/부분/미완료, 해당 AC·시험 ID.
- 실제 실행한 시험과 결과 파일, 실패·미수행 이유.
- fixture/live, 모델 단계 완료/사람 도움 완료, 오류 주입/자연 생성의 구분.
- 사용자 선택을 변경한 뒤 생성된 실제 공개 파일과 hash, 과거 파일의 무효화 결과.
- 독립 수신자가 공개 자료만으로 수행한 다음 행동.
- 알려진 제한과 다음 작업. 시간·호출 수·수정 횟수는 실제 측정값만 기록.

검증 보고 양식은 [report-template.json](../evaluation/results/report-template.json), 시험 목록은 [qa.md](qa.md), 설명 시연은 [demo.md](demo.md)를 사용한다.

## 웹·엔진 분리 시험

새 구현의 진입점은 [독립 실행 계약](separated-runtime.md)이다. `just demo-start`와 `just live-start`를 별도로 실행하고 `just test-engine-live`로 웹 없이 실제 엔진을 시험한다. `just check`는 QG를 직접 호출하며 npm test는 Node 테스트만 담당한다.
