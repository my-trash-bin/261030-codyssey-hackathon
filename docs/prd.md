# SafeHandoff PRD

> 보존한 제품 설계/이전 기록이다. 현재 구현은 TypeScript 서버/클라이언트의 문서 저장/조회만 제공한다. 현재 실행과 API는 [README](../README.md) 및 [api](api.md)를 따른다.

현재 웹/엔진 분리 시험 경로와 실제 구현 범위는 [독립 실행 계약](separated-runtime.md)을 따른다. 기존 전체 기능 계약과 새 시험 경로의 구현 완료를 구분한다.

문서 버전: 1.0 / 기준일: 2026-10-31 / 상태: 구현 기준안

이 문서는 [intent.md](../intent.md)의 제품 의도 안에서 **무엇을 만들고, 누구의 어떤 일을 줄일지** 정한다. intent 변경 권한은 [AGENTS.md](../AGENTS.md)를 따른다. 동작의 상세 규칙은 [spec.md](spec.md), 공통 데이터와 API는 [ERD.md](ERD.md)와 [api.md](api.md), 화면은 [IA.md](IA.md), 사용자 여정은 [uj.md](uj.md)를 따른다. 각 기능의 구현 범위는 [features](features/01-task-intake.md)에 나누어 둔다.

이 묶음은 설계 문서다. 앱이 이미 구현되었거나, 시간 절감/검사 성능이 측정되었다는 뜻은 아니다. 대화에서 정한 제품 방향을 **U(사용자 확정)**, 이를 구현 가능하게 구체화한 선택을 **D(PoC 기본 설계)**, 실제 회사에서 받아야 할 정보를 **Q(확인 필요)**로 구분한다. D는 팀이 같은 구현 결과를 만들기 위한 기본값이며 변경할 때 관련 문서를 함께 바꾼다.

## PRD-01 - 목적과 핵심 가치

**회사 자료를 외부에 공유하기 전에, 공유 목적에 필요한 자료를 준비하는 사람의 수고를 줄인다.**

개발자가 라이브러리 오류를 제보하려고 로그를 보면 회사의 함수명/내부 경로/업무 내용이 함께 들어 있을 수 있다. 공급사에 장애를 문의하려는 담당자는 문제를 조사할 단서는 남기고 회사 정보는 덜 공개할 범위를 직접 골라야 한다. 이름을 가리는 것만으로 준비가 끝나지 않을 때도 있고, 너무 많이 지우면 수신자가 조사할 수 없는 자료가 된다. 가상 자료를 만들어도 같은 현상이 나타나는지 확인하는 일은 남는다.

SafeHandoff는 목적과 원자료를 읽고 필요한 정보와 공개 수준을 제안한다. 사람이 선택하면 선택한 범위로 새 문서/표/예제를 만들고 작성 중 검토한다. 재현 환경이 준비된 경우에는 새 예제로 정해진 현상이 나타나는지도 확인한다. 최종 자료를 확인하고 공유하는 주체는 사용자다.

**주요 가치 가설(U):** 같은 공개 조건과 수신자 효용을 만족하는 자료를 준비할 때, 사람이 읽고/판단하고/다시 쓰고/검증하는 작업량이 줄어든다. 조건에 맞는 판단과 제품별 지침을 재사용하면 반복 업무에서도 도움이 될 수 있다. 이것은 PoC에서 검증할 가설이며 미리 보장하는 수치가 아니다.

## PRD-02 - 대상과 대표 사례

| 대상 | 시작 상황 | 사용자가 이루려는 일 | 완료된 결과 |
| --- | --- | --- | --- |
| 오픈소스 라이브러리를 사용하는 개발자 | 제품에서 오류를 관찰했지만 회사 로그를 그대로 공개하기 어렵다 | 공개 issue에서 조사 가능한 기술 조건을 설명한다 | 제보문, 필요한 환경 정보, 준비된 경우 새 재현 예제/실행 방법/실제 확인 결과 |
| B2B 제품을 사용하는 개발/운영/지원 담당자 | 공급사가 기록을 요청했지만 서버 환경이나 재현 장비는 없다 | 공급사가 다음 조사를 시작할 자료를 만든다 | 관찰 사실, 승인한 추적 ID, 미확인 사항, 조사 질문을 담은 문의문 |
| 외부 자문을 받는 내부 업무 담당자 | 업무 현황/메모를 전달하려고 한다 | 규모나 고객 정보를 제한하면서 업무 구조를 설명한다 | 업무 설명, 선택한 수준의 새 표, 유지해야 할 제약, 자문 질문 |

첫 두 사례가 메인이다. 일반 내부 자료는 같은 흐름이 로그 이외에서도 작동하는지 확인하는 사례다. 스크린샷 이름 가리기는 필요성을 설명하는 비유로 쓸 수 있으나 첫 구현의 주 대상이나 입력 형식이 아니다.

### 사용자와 권한의 제품 범위

- PoC의 실제 사용자는 **한 회사 안에서 자기 컴퓨터로 작업하는 자료 작성자 한 명**이다. 이 사용자가 공개 수준을 정하고 결과를 확정한다.
- 설치 운영자는 앱 설정/사내 모델 연결/확장 설치를 준비한다. PoC에서는 같은 사람이 두 역할을 맡아도 된다. 별도 조직 관리 화면은 만들지 않는다.
- 외부 수신자는 결과물을 받는 사람이다. 앱 계정이나 원자료 접근 권한을 얻지 않는다.
- 분석/작성/검토 에이전트는 사용자 역할이 아니다. 공개 승인/최종 확정/규칙 활성화 권한이 없다.
- 실제 회사에서 누가 자료 반출을 승인할 자격이 있는지는 Q다. PoC의 확인 버튼을 회사의 공식 결재 시스템으로 설명하지 않는다.

## PRD-03 - 실행 환경과 운영 형태

**U:** 회사별로 설치/운영하는 오픈소스 프로젝트다. 여러 회사의 원자료를 중앙 사업자 서버에 모으는 서비스를 전제로 하지 않는다. 이미 사용 가능한 사내 LLM을 연결한다. 특정 모델, GPU, VRAM, 양자화/추론 최적화를 기능의 선행 조건으로 요구하지 않는다.

**D:** 첫 구현은 Go 단일 앱, SQLite, 서버 HTML와 순수 JavaScript로 만든다. 기본 접속은 `127.0.0.1`이며 사용자가 명시하면 사내 네트워크의 서버 IP로 접속할 수 있도록 wildcard 또는 특정 IP에 바인딩한다. Host 허용 목록과 같은 Origin/세션/CSRF 검사는 유지한다. 준비 작업 환경의 인터넷 연결은 차단하고, 설정된 사내 모델 연결만 허용한다. 원자료를 읽는 에이전트에는 외부 제출 기능을 주지 않는다. 앱 자체의 세션/요청 검증과 실행 경계는 [F10](features/10-runtime-boundary.md)에 정의한다.

원자료를 처리하는 실행 환경, OS 운영자, 설정한 사내 모델 서비스는 신뢰 경계 안에 있다. 오픈소스로 배포한다는 사실만으로 모든 배포 환경의 안전성이 보장되지는 않는다. 사용자는 회사에서 제공한 저장/연결 환경과 자료 취급 규칙을 적용해야 한다.

## PRD-04 - 목적/수신자/자료 입력

사용자는 다음을 지정하고 자료 분석을 시작한다.

| 항목 | 첫 구현의 규칙 |
| --- | --- |
| 내부 작업 이름 | 이력에서 찾기 위한 내부 이름. 공개 문서 제목으로 자동 복사하지 않는다 |
| 프로젝트 | 운영 설정에 등록된 ID를 선택한다. 추가가 필요하면 실행 환경 안내에서 설정 절차를 확인한다. 이름 자체는 내부 정보다 |
| 목적 | `oss_issue`, `vendor_support`, `operations_advice` 중 하나 |
| 이번 문의의 목표 | 목적 안에서 허용된 goal_variant 선택. 기본은 default |
| 수신자/범위 | 공개 대상 `public` 또는 등록한 특정 외부 수신자 `named_external` |
| 결과 언어 | 첫 구현은 한국어/영어. 입력 자료의 언어와 별개 |
| 제품별 지침 | 설치된 지침을 선택. 지침이 없으면 공통 작성 흐름을 사용 |
| 원자료 | UTF-8 텍스트 붙여넣기, `.txt`, `.log`, `.md`, `.csv`, `.json` |

자료 업로드는 외부 공개 승인이 아니다. 지원하지 않는 형식/해석 실패/크기 초과는 파일별 이유를 보여주며, 일부 파일을 조용히 빼고 전체 분석 완료로 표시하지 않는다. 자료가 없으면 분석을 시작할 수 없다. 목적/수신자/자료는 작성 중에도 변경할 수 있으나 기존 결과의 유효성이 함께 바뀐다.

goal_variant는 이번 결과의 목표다. OSS는 `default`/`observations_only`/`reproduction_evidence`, 공급사 문의는 `default`/`observations_only`/`ask_for_diagnostics`와 등록된 실행 팩이 있을 때 `reproduction_evidence`, 운영 자문은 `default`만 지원한다. 목표 변경은 새 revision과 재분석/재결정으로 이어진다. default는 재현 확인 없이도 관찰 문의를 완성할 수 있다.

## PRD-05 - 근거 있는 제안과 작성 중 질문

시스템은 원자료에서 관찰, 제약, 가설, 미확인 내용을 구분하고 근거를 연결한다. 제안에는 해당 내용이 목적에 필요한 이유와 공개 선택별 미리보기가 있어야 한다. 사용자가 원자료 근거를 직접 열 수 있어야 한다.

처음부터 모든 질문에 답해야만 초안을 볼 수 있는 흐름으로 제한하지 않는다. 현재 승인한 정보로 미완료 초안을 보면서 추가 질문에 답할 수 있다. 질문은 관련 내용을 묶어 보여주되 필요한 판단을 숨기지 않는다. 보류 중인 항목은 화면에 남으며 최종 확정 전에 결정하거나 이번 결과에서 제외해야 한다.

요청량 질문은 다음 네 선택지를 유지한다.

| 선택지 | 실제로 공개하는 정보 |
| --- | --- |
| A. 구체적인 데이터 없이 사실만 | 예: 관찰된 구간에서 요청량이 증가했다는 사실. 건수/비율/관찰 개수/시간 간격은 별도 허용 없으면 제외 |
| B. 추이만 보이게 나머지 마스킹 | 선택한 관찰 순서와 변화 방향으로 새 표를 작성. 관찰 개수/순서는 포함, 실제 건수/증가율/날짜/간격은 제외 |
| C. 요청 정보 마스킹 | 실제로 남길 필드와 값을 고른 뒤 그 공개 미리보기를 승인. 선택한 필드로 새 표를 작성 |
| D. 기타 (직접 입력) | 예: 첫 관찰을 100으로 한 상대지수. 지원 변환으로 해석한 내용과 실제 미리보기를 확인하고 적용 |

여기서 '마스킹'은 사용자가 이해할 공개 수준의 이름이다. 원자료 전체를 복사한 뒤 특정 칸만 지워 전달하는 생성 방식을 뜻하지 않는다. 승인한 정보로 새 결과물을 구성한다. 자유 입력을 지원할 수 없거나 해석이 모호하면 이를 설명하고 다시 선택하게 한다.

제품 템플릿이 정한 필수 정보와 모델이 중요하다고 추천한 정보는 구분한다. 모델의 추천만으로 영구적으로 확정을 막거나 공개를 강제하지 않는다. 사용자는 추천을 제외할 수 있고, 등록된 목표의 필수 정보가 부족한 경우에만 보완하거나 목표를 조정한다.

## PRD-06 - 승인한 정보로 새 자료 작성

**U:** 전체 새 작성이 기본이다. 원문 또는 정확한 실제 값을 유지해야 하면 사용자에게 그 내용/범위를 보여주고 별도로 허용받는다.

다음 세 동작을 섞지 않는다.

1. **사실/표현 수준 선택:** 어떤 의미를 어느 정도의 상세함으로 새 문장/표에 사용할지 정한다.
2. **정확한 값/원문 구간 허용:** 이번 자료의 특정 값 또는 지정 판본의 지정 구간을 확인하고 허용한다. 주변 내용까지 허용하지 않는다.
3. **최종 파일 확정:** 실제로 완성된 본문과 첨부를 확인한다. 앞 단계에서 허용하지 않은 공개를 이 버튼으로 일괄 승인하지 않는다.

앱이 현재 유효한 결정으로 작성용 정보 묶음을 만든다. 작성기는 그 묶음과 등록된 공개 작성 지침만 받는다. 내부 파일명/자유로운 목적 메모/미승인 후보/분석 대화가 작성기에 자동 전달되지 않는다. 새로 만든 내용도 선택한 의미를 과장하거나 근거 없는 원인을 덧붙이면 수정해야 한다.

## PRD-07 - 작성 중 검토와 사람의 복구 경로

작성기와 검토기가 반복하며 현재 공개 결정, 자료의 근거, 누락한 중요한 조건, 사실과 가설의 구분을 확인한다. 검토기는 필요한 경우 작성 단계에서 사용자에게 질문을 돌려보낸다. 최종 파일 구성 이후에도 실제 본문/표/첨부를 검사한다.

작은 모델이 형식을 틀리거나 검토를 끝내지 못할 수 있다. 제한된 자동 재시도 후 사용자는 근거 있는 후보를 직접 추가하거나 초안을 수정하고, 필요하면 현재 파일의 의미를 직접 검토할 수 있다. 사람이 검토한 결과와 모델이 통과시킨 결과를 별도로 기록한다. 사람이 체크했다고 만료 승인, 잘못된 참조, 오래된 파일, 필수 검사 실패가 무시되지는 않는다.

## PRD-08 - 선택 변경과 같은 파일 내보내기

공개 수준/수신자/자료/언어/적용 지침을 바꾸면 영향받은 결과를 즉시 '이전 선택의 결과'로 표시한다. 새로 작성하는 동안 이전 결과의 복사/다운로드는 사용할 수 없다. 늦게 완료된 이전 실행이 현재 선택을 덮어쓰지 않는다.

최종 확인은 공유할 파일 전체를 대상으로 한다. 파일명/본문/첨부 내용과 검사 상태를 보여주고 사용자가 `이 파일들로 확정`을 누른다. 다운로드는 확인한 것과 동일한 저장 바이트를 반환하고, 본문 복사는 확정 UTF-8 파일을 해석한 텍스트를 사용한다. 다시 모델을 호출하지 않는다. 자료를 자동으로 외부에 제출하지 않는다.

## PRD-09 - 조건에 맞는 판단 재사용

저장하는 것은 표현 기준과 그 적용 범위다. '이 프로젝트에서, 이 공급사의 문의에, 요청량의 방향만 표시'처럼 사람이 읽을 수 있어야 한다.

- 등록된 프로젝트/목적/goal_variant/수신자/공개 범위/지침 판본과 검증 가능한 자료 스키마/선택자가 맞는 경우에만 변환 기준을 적용한다.
- 새 자료의 방향/비율은 새로 계산한다. 이전 문장/결과를 새로운 사실처럼 사용하지 않는다.
- 일반 문서의 비슷한 사례는 제안으로 보여준다. 모델이 비슷하다고 판단한 사실만으로 공개를 허용하지 않는다.
- 정확한 값과 원문 구간의 허용은 이번 자료에 묶이며 재사용하지 않는다. C에서 실제 값을 골라도 동일하다.
- 사용자는 기준을 수정/중지할 수 있고, 철회/만료되면 현재 결과의 영향도 확인할 수 있어야 한다.

## PRD-10 - 제품별 지침과 맥락 예외

설치된 제품/라이브러리별 추가 기능은 먼저 확인할 질문, 필요한 버전/환경 정보, 제보 양식, 고정 변환, 검사 방법을 제공한다. 첫 구현에는 지침 등록과 실제 맥락 검사 예제를 포함한다. 라이브러리별 기능이 가치를 만드는지 확인할 수 있도록 지침 없는 공통 흐름과 함께 동작해야 한다.

패턴 검사에서 IP가 발견돼도 출처와 목적에 따라 판단이 달라질 수 있다. 예를 들어 승인한 가상 설정 예시의 주소인지 실제 접속 로그에서 가져온 주소인지 검사한다. 맥락 예외는 해당 검사 지적을 해소할 뿐 공개 허가를 새로 만들지 않는다. 등록된 검사 프로그램만 실행하며 사용자가 업로드한 임의 스크립트를 바로 실행하는 UI는 만들지 않는다.

## PRD-11 - 재현 확장과 재현할 수 없는 문의

준비된 대상/실행 환경/판정 기준이 있으면 승인 범위로 만든 새 입력을 실행해 정해진 현상을 확인한다. 첫 PoC는 고정된 가상 라이브러리의 결함/수정 버전과 정상/후보 입력을 비교한다. 실제 결과를 `reproduced`, `not_reproduced`, `inconclusive`, `error`, `not_run`으로 구분한다.

재현 실패만으로 공개 범위를 넓히지 않는다. 입력 조건이 부족한지, 대상/환경이 맞는지, 실행 오류인지 확인하고 필요할 때 공개 선택으로 돌아간다. 같은 증상이 나타났다는 결과를 동일한 근본 원인의 증명으로 표현하지 않는다.

재현 환경이 없으면 관찰 사실과 미확인 사항으로 문의를 완성할 수 있다. 재현 확인을 목표로 삼았던 작업에서 이를 생략하려면 사용자가 문의 목적을 관찰 공유로 좁히는 선택을 해야 한다. 준비된 재현 자료는 수신자가 회사 원자료 없이 실행하고 수정 전후를 비교하는 데 도움이 될 수 있다.

`goal_variant=reproduction_evidence`는 정해진 재현 확인이 완료돼야 확정할 수 있다. 실패/환경 없음이면 사용자가 `observations_only`로 명시적으로 바꾸고 필요한 정보를 다시 평가한다. 모델이나 finalize가 목표를 자동으로 낮추지 않는다.

## PRD-12 - 진행 상황/복구/보존/삭제

사용자는 현재 단계, 결정이 필요한 이유, 마지막 완료 단계, 재시도 가능한 동작을 볼 수 있어야 한다. 알 수 없는 진행률을 퍼센트로 꾸며 표시하지 않는다. 새로고침과 연결 복구 뒤에도 저장한 선택이 남아야 한다.

**D:** 원자료와 작업 결과는 사용자가 해당 작업을 삭제할 때까지 내부 DB에 남는다. 프롬프트/응답 원문 진단 기록은 기본적으로 저장하지 않는다. 명시적으로 디버그 기록을 켠 경우 본문은 24시간 보관하고 작업 삭제 시 함께 삭제한다. 기본 실행 메타데이터는 이력으로 남는다.

작업 삭제는 원자료/근거/결정/초안/공개 파일/실행 기록을 앱에서 제거한다. 저장한 재사용 기준은 별도의 자료이며 원문을 담지 않는 범위/변환 규칙으로 계속 남는다. 삭제 확인에서 이 차이를 설명하고, 사용자가 원하면 기준 관리로 이동해 별도로 철회할 수 있게 한다. 이미 다운로드한 파일과 OS 백업을 회수하거나 저장 매체의 복구 불가능한 삭제를 보장하는 기능은 아니다.

## PRD-13 - 검증할 효과와 완료 수준

### 기능 검증

| 수준 | 필요한 증거 |
| --- | --- |
| P0 core 구현 완료 | 입력->결정->새 작성/검토->동일 파일 확정, 변경/복구/재사용/권한 시험을 개발용 응답으로 통과 |
| P0 live 확인 | 실제 사내 모델로 세 대표 사례 수행. 형식 실패/수동 개입/재시도/미완료를 숨기지 않고 기록 |
| P1 확장 확인 | 등록 지침/맥락 예외 검사와 고정 toy 재현을 실제 실행하고, 수신자가 공개 자료만으로 다음 행동 수행 |
| 전체 PoC 검증 완료 | P0/P1의 필수 검증과 [qa.md](qa.md)의 완료 기준 충족, 실패/미수행/적용 한계를 포함한 보고서 |

fixture 통과, live 연결, live에서 사람 도움으로 완료, live에서 모델 단계까지 완료는 다른 결과다. 기능이 구현됐다는 말과 가치가 입증됐다는 말을 구분한다.

### 가치 비교

직접 준비, 같은 사내 LLM의 충분히 준비된 일반 대화, SafeHandoff를 비교한다. 일반 대화에도 같은 자료/공개 기준/제품 지침/이전 결정/기본 도구/수정 기회를 제공한다. 모델이 다른 조건을 비교해 제품 효과로 해석하지 않는다.

측정 항목은 사람의 실제 작업 시간, 총 경과 시간, 질문/수정/수동 판단 횟수, 선택 기준 위반, 필수 정보 누락, 수신자의 첫 유효 행동 및 추가 질문이다. 첫 사용과 반복 사용을 구분하고 지침/검사기를 준비한 시간도 별도로 기록한다. 사용자 대기 시간과 모델 처리 시간을 섞어 '업무 시간 절감'으로 표기하지 않는다. 측정 전 목표 절감률을 성과처럼 발표하지 않는다.

## PRD-14 - 범위와 약속의 한계

| 우선순위 | 포함 범위 |
| --- | --- |
| P0 core | F01 입력, F02 근거 분석, F03 공개 선택, F04 작성/검토, F05 확정/내보내기, F06 재사용, F09 이력/복구, F10 실행 경계 |
| P1 확장 검증 | F07 제품별 지침/맥락 예외, F08 합성 재현. 이번 PoC 설계에 포함하며 P0 완료와 별도 단계로 구현 |
| P2 후속 | 자동 티켓 제출, PDF/DOCX/OCR/스크린샷 처리, 다중 사용자/SSO/조직 결재, 외부 SaaS 연결, 사용자 임의 코드/스크립트 실행, 확장 마켓, 대용량 검색/문맥 압축/모델 최적화 |

다음은 약속하지 않는다.

- 민감한 의미나 외부 지식과 결합한 추론 가능성을 모두 찾아낸다는 보장.
- 마스킹 도구보다 항상 안전하거나 준비 시간이 항상 줄어든다는 보장.
- 임의 버그를 자동으로 찾아내거나 언제나 재현 예제를 만든다는 보장.
- 어떤 작은 모델에서도 동일한 자동 성공률을 낸다는 보장.
- 악의적인 호스트 운영자, 감염된 OS, 별도 외부 업로드 경로까지 통제한다는 보장.
- 사용자가 이미 내려받거나 공유한 파일을 회수한다는 보장.

본 프로젝트의 확장성은 제품/라이브러리별 준비 절차, 검사, 재사용 가능한 판단을 더할 수 있다는 데 있다. 유료 구독/과금/매출 목표는 이번 제품 요구사항이 아니다. 오픈소스 적용 가능성과 실제 자료 준비 효과를 먼저 평가한다.

## 구현 전에 필요한 실제 정보

실제 회사 설정은 [decisions.md](decisions.md)의 Q 항목에 기록한다. 사내 모델 endpoint/인증 방식, 실제 반출 승인권자와 정책, 적용할 실제 라이브러리/공급사, 실제 지침의 사용 조건은 추정하지 않는다. 이 정보가 없어도 가상 자료와 fixture provider로 P0 구현을 시작할 수 있다.

## 변경 원칙

intent 변경이 필요한 경우 명시적 승인 후 intent부터 갱신한다. 그 범위 안에서 제품 범위/사용자 약속을 바꾸면 이 문서를 먼저 또는 같은 PR에서 고친다. 상태/권한/판본/자료 계약이 달라지면 spec/ERD/API와 해당 기능 파일/시험을 같은 변경으로 맞춘다. 기능 파일에서 새 결정을 만들고 상위 문서를 그대로 두지 않는다. 이전 발표자료와 충돌하면 최신 제품 결정과 이 구현 기준을 맞추고 변경 이유를 결정 기록에 남긴다.
