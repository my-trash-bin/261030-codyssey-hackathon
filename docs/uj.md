# SafeHandoff 사용자 여정

문서 버전: 2.0 / 기준일: 2026-10-31 / 상태: 현행 정본

목표는 사람이 원자료에서 유용한 공유본을 만드는 흐름을 끝까지 정의하는 것이다. 각 단계의 화면은 [IA](IA.md), 동작 규칙은 [spec](spec.md), 검증 자료는 [test-data](test-data.md)를 따른다. 아래 예시는 모두 가상 데이터다. '시스템 완료'는 실제 검사/저장 결과가 있는 경우만 의미한다.

## 1. 모든 사례의 공통 흐름

| 단계 | 사용자가 하는 일 | 시스템이 하는 일 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 1. 목적과 자료 준비 | 목적/수신자/원자료를 선택 | 형식/크기/범위를 확인하고 불변 자료 판본 저장 | 유효한 자료와 목적 존재 |
| 2. 공개 범위 선택 | 필요한 이유/근거/선택별 결과를 보고 결정 | 근거 있는 후보와 공개 미리보기 제시 | 사용할 정보에 현재 유효한 결정 존재 |
| 3. 새 작성과 검토 | 진행/초안을 보며 추가 질문에 답함 | 승인한 정보로 새 자료 작성, 작성 중 검토/수정 | 현재 결정과 일치한 파일 구성 가능 |
| 4. 목적 달성 확인 | 부족한 정보/재현 결과를 확인 | 누락/미확인/실패를 구분하고 대안 제시 | 현재 목표에 필요한 검사 완료 또는 사용자 목표 조정 |
| 5. 파일 확인 | 실제 본문/첨부/원문 구간을 확인 | 현재 판본/해시/승인 다시 검사 | 사용자가 현재 파일들을 확정 |
| 6. 결과 사용 | 본문 복사 또는 파일 다운로드 후 직접 공유 | 같은 저장 바이트 반환 | 수신자에게 준비한 자료를 전달할 수 있음 |

2->3만 있는 일방향 흐름이 아니다. 작성/검토 중 필요한 정보가 부족하거나 재현 조건을 다시 골라야 하면 3/4->2로 돌아간다. 더 공개할지, 덜 구체적인 문의로 바꿀지, 현재 결과에서 해당 내용을 제외할지는 사람이 선택한다.

## UJ-01 - 오픈소스 라이브러리 오류 제보

### 시작 상황

개발자가 회사 제품에서 가상 라이브러리 `toyrecord`의 다중 바이트 문자열 처리 오류를 관찰했다. 로그에는 고객 문자열/내부 경로/비공개 업무 내용이 들어 있다. 공개 제보문과 회사 문자열을 쓰지 않는 작은 실행 예제를 준비하고 싶다.

| 단계 / 화면 | 사용자 행동 | 시스템 응답 | 확인할 결과 |
| --- | --- | --- | --- |
| 입력 / UI-02 | `오픈소스 버그 제보`, 공개 수신자, 한국어 또는 영어, toyrecord 추가 기능 선택. 로그/메모/관찰표 등록 | 파일 해석 결과, 원자료가 내부에 저장됨 표시 | 업로드는 공개 허용으로 처리되지 않음 |
| 분석 / UI-03 | 분석 시작 | 오류 단계/제품 버전/문자열 특성/불확실성을 근거와 함께 후보로 제시 | 고객 이름/사업 메모는 기술 관찰과 구분 |
| 결정 / UI-04 | 기술 관찰/공개 입력 계약을 허용. 고객 문자열/원래 길이/시각/경로/사업 정보 제외 | 선택마다 실제 공개될 의미를 보여줌 | 공개 버전과 오류 조건이 남고 회사 고유 데이터는 사용하지 않음 |
| 새 예제 / UI-03 | 공개 계약에 따른 새 ASCII/한글 입력 실행을 선택 | 원래 7글자 문자열과 별개의 새 6글자 입력을 생성, 고정된 buggy/fixed 대상에서 실행 | 실제 네 실행 결과 저장 |
| 검토 / UI-03 | 초안과 실측 결과 확인 | 정해진 증상 확인 여부, 미확인 원인 표시. 승인되지 않은 문장은 수정 | 재현 관찰을 근본 원인 확정으로 바꾸지 않음 |
| 최종 / UI-06 | 제보문/실행 방법/새 입력/결과/공개 target 파일 확인 후 확정 | 현재 파일 해시/승인/검사 확인 | 공유 패키지에 원자료/내부 이력 없음 |
| 사용 / UI-06 | 패키지 다운로드 | 같은 확정 바이트 반환 | 수신자가 앱/회사 DB 없이 재현 예제를 실행 가능 |

### 실패/경계 분기

- **실행 환경 없음:** `재현 실행 안 함 - 환경 없음`을 표시한다. 사용자가 goal_variant를 `observations_only`로 바꿔 문의 목표를 좁히면 제보문은 완성할 수 있다. 이 작업을 재현 확인 성공으로 집계하지 않는다.
- **새 입력에서 오류가 안 남:** 결과는 `not_reproduced`다. 대상과 입력 조건을 확인하고 공개 범위 선택으로 돌아갈 수 있다. 원래 고객 문자열을 자동 사용하지 않는다.
- **다른 단계에서 실패:** 실행/대조군/판정 조건에 따라 `inconclusive` 또는 `error`다. 목표 오류 재현으로 표시하지 않는다.
- **사용자가 원문 오류 줄을 원함:** 실제 구간/판본/공개 형태를 확인하는 원문 허용을 별도로 만든다. 주변 경로/고객 문자열까지 자동 포함하지 않는다.
- **외부 수신자가 다시 질문:** 같은 작업의 선택을 바꾸거나 새 자료를 추가하면 새 판본으로 작성한다. 과거 확정 결과는 현재 공유본이 아니다.

### 완료의 관점

사용자는 회사 자료를 직접 대대적으로 가공하지 않고 제보문/작은 예제/확인 결과를 준비했다. 수신자는 공개 파일만으로 정해진 현상을 확인할 수 있다. 일반 라이브러리의 모든 버그를 자동 재현한다는 뜻은 아니다.

## UJ-02 - 재현 환경 없는 B2B 기술지원

### 시작 상황

운영 담당자가 가상의 VendorStore에 저장 요청을 보냈다. 최초 요청은 클라이언트 응답 대기 시간이 초과됐고 재시도는 성공 응답을 받았다. 최초 서버 처리와 중복 여부는 모른다. 공급사 서버에 접근하거나 같은 상황을 직접 재현할 수 없다.

| 단계 / 화면 | 사용자 행동 | 시스템 응답 | 확인할 결과 |
| --- | --- | --- | --- |
| 입력 / UI-02 | `B2B 기술지원`, 지정 공급사, 로그/요청량 표/메모 입력 | 공급사와 공개 범위를 내부 ID로 고정 | 다른 공개 issue와 범위가 구별됨 |
| 분석 / UI-03 | 근거 확인 | timeout 관찰, 재시도 성공 응답, 최초 완료/중복/인과관계 미확인을 분리 | '첫 저장 실패'라고 임의로 결론 내리지 않음 |
| 요청량 / UI-04 | A 또는 B 선택 | 사실만 문장 또는 방향 표 생성 | 실제 건수/증가율/시각을 선택 없이 남기지 않음 |
| 식별자 / UI-04 | 이번 문의에서 operation_id와 attempt_id 정확한 값 사용 허용 | 실제 값과 목적/수신자 범위를 미리보기 | 정확값 허용은 이번 자료만, 자동 재사용 없음 |
| 작성 중 / UI-03 | 추가 질문에 응답 | 관찰/모르는 점/공급사 조사 질문 작성, 검토 | 공급사만 가진 결과를 알고 있는 것처럼 쓰지 않음 |
| 최종 / UI-06 | `재현 실행 안 함 - 환경 없음` 확인, 파일 확정 | 미재현 상태와 문의 준비 완료를 함께 표시 | 재현이 없어도 유용한 문의 완성 |
| 수신자 확인 | 공급사 역할 평가자가 공개 자료만 확인 | 승인한 ID로 별도 공급사 기록 조회 | 다음 조사 또는 필요한 추가 정보를 제안 가능 |

### 정확한 ID를 공개하지 않는 분기

사용자가 ID를 제외하면 이를 존중한다. 시스템은 개별 요청 조회가 어려워질 수 있음을 설명하고 사용자가 `goal_variant=ask_for_diagnostics`로 바꾸도록 안내한 뒤 '조회에 필요한 최소 식별 정보와 안전한 재시도 조건을 알려 달라'는 문의로 조정한다. ID 없는 결과에서 공급사 로그를 조회했거나 중복 처리가 확인됐다고 쓰지 않는다.

### 수신자 변경 분기

공급사 문의를 공개 커뮤니티 질문으로 바꾸면 기존 정확값/원문 허용과 공급사에 한정된 저장 기준을 자동 승계하지 않는다. 작업은 현재 범위에서 결정이 필요한 상태로 돌아간다. 사용자가 새 범위에서 선택하면 새 공유본을 만든다.

### 추가 B2B 응용: 정산 파일

실제 계약 단가/거래 금액을 포함한 파일을 공급사에 전달하기 어려운 경우에도 같은 준비 흐름을 적용할 수 있다. 첫 구현은 그 업무의 범용 결함 탐지기를 요구하지 않는다. 제품별 실행기와 판정 기준이 준비된 경우에만 새 파일로 같은 현상을 확인하는 확장으로 다룬다. 아직 실행기가 없으면 관찰/조건/문의문을 준비하고 재현 상태를 미수행으로 남긴다.

## UJ-03 - 일반 내부 자료로 외부 자문 받기

### 시작 상황

업무 담당자가 외부 운영 자문사에 반복 업무 개선을 묻는다. 자료에는 관찰 구간별 요청량 820/1,160/1,740, 접수표와 처리 시스템의 중복 입력, 사람이 상태를 대조하는 흐름, 기존 메일/메신저 채널을 유지해야 한다는 제약이 있다. 실제 규모/기간/고객은 덜 공개하고 싶다.

| 단계 | 사용자 선택 | 시스템 결과 |
| --- | --- | --- |
| 목적/자료 등록 | `일반 내부 자료 / 외부 운영 자문`과 지정 수신자 선택, CSV/Markdown 입력 | 업무 사실/제약/요청량 후보와 근거 |
| A 선택 | `구체적인 데이터 없이 사실만` | `관찰된 구간에서 요청량이 증가했습니다.`라는 문장. 실제 값/관찰 개수/배수 없음 |
| B로 변경 | `추이만 보이게 나머지 마스킹` | 새 표: 첫 번째 기준, 두 번째 증가, 세 번째 증가. 관찰 개수/순서는 보임 |
| C 선택 | 예: 요청 건수만 실제 값으로 허용, 기간/고객 제외 | 남길 실제 필드/단위/값 미리보기 후 승인, 새 표 작성 |
| D 선택 | `규모는 숨기고 첫 관찰 대비 지수만` | 지원 변환 해석 후 100/141/212 미리보기, 사람이 적용하면 새 표 작성 |
| 업무 제약 허용 | 중복 입력/수동 대조/기존 채널 유지 조건 허용 | 요청량 표현을 바꿔도 업무 제약은 유지 |
| 최종 확인 | 선택한 결과의 본문/표 확인 | 선택에 맞는 파일만 확정/다운로드 |

A/B/C/D는 하나의 작업에서 동시에 자동 공개할 여러 버전이 아니다. 현재 선택 하나에 대응하는 결과를 생성하며 비교 미리보기는 내부 화면이다. C의 실제 값과 D의 비율을 봤다는 이유만으로 B 결과에 함께 남기지 않는다.

### 다음 달 자료에 기준 재사용

사용자가 B의 방향 표 기준을 같은 범위에 저장했다. 새 자료가 820/780/1,740이면 적용 조건을 확인한 뒤 새로 계산하여 감소/증가를 표시한다. '지난번에도 증가했으므로 이번에도 증가'로 쓰면 실패다. 새로운 고객/원문/정확한 숫자 허용은 저장 기준으로 넘어오지 않는다.

## UJ-04 - 작성 중 선택을 바꾸기

1. 현재 작업은 revision 8에서 비율 표가 있는 초안을 작성 중이다.
2. 사용자가 A '사실만'으로 바꾸고 실제 공개 미리보기를 승인한다.
3. 서버는 선택 배치를 저장하면서 revision 9를 만들고 revision 8 결과를 stale로 표시한다. UI는 즉시 이전 파일의 복사/다운로드를 비활성화한다.
4. 이전 모델 호출이 뒤늦게 끝나도 현재 작업 포인터를 바꾸지 않는다.
5. revision 9의 승인된 정보로 전체 문서/표/첨부를 다시 구성한다. 비율을 담은 이전 첨부가 남아서는 안 된다.
6. 사용자가 현재 파일들을 다시 확인하고 확정한다.

직접 편집한 문장도 새 작성으로 바뀔 수 있음을 선택 변경 때 알린다. 이전 문장은 내부 이력에서 참고할 수 있으나 새 공개 결정 대신 복원하지 않는다.

## UJ-05 - 작은 모델의 오류와 수동 복구

| 실패 위치 | 사용자에게 보이는 상태 | 가능한 복구 | 불가능한 우회 |
| --- | --- | --- | --- |
| 분석 형식 오류 | 후보를 확인하지 못함 | 제한 재시도, 근거 있는 후보 수동 추가 | 원자료 전체를 공개 초안으로 사용 |
| 직접 조건 해석 모호 | 조건을 더 정해야 함 | 문장 수정 또는 지원 선택지 | 자연어를 그대로 실행 코드/권한으로 사용 |
| 작성 형식/내용 오류 | 초안 수정/검토 필요 | 재시도, 현재 승인 정보 범위에서 직접 편집 | 편집 내용의 새 사실을 자동 승인 |
| 의미 검토 미완료 | 사람 확인 필요 | 현재 파일과 의미 항목을 사람이 검토, human 기록 | 판본/참조/만료/필수 검사 실패 우회 |
| 모델 연결 실패 | 실제 모델에 연결하지 못함 | 설정 복구 후 명시적 재시도 | 개발용 응답으로 몰래 대체 |
| 입력 문맥 초과 | 일부 또는 전체 자료를 처리하지 못함 | 자료 선택 범위 조정/다시 분석 | 조용히 앞부분만 읽고 전체 완료 |

미해결 오류가 있으면 검토 완료로 표시하지 않는다. 수동 작업을 통해 완료한 경우에도 사람이 무엇을 했는지 이력/평가에 남긴다.

수동 후보/user_note 추가는 새 revision과 새 후보 집합을 만든다. 원래 후보의 과거 결정은 새 후보 ID로 자동 이전하지 않는다. 이전 선택은 참고로 보고 다시 확인하거나 현재 범위에 맞는 등록 변환 기준을 적용한다. 새 메모를 작성기가 곧바로 읽게 하지 않는다.

## UJ-06 - 새로고침/중단/다른 창

- **새로고침:** 서버의 현재 작업/결정/job 상태를 다시 읽는다. 화면에 남은 메모리 상태를 정답으로 삼지 않는다.
- **브라우저 연결 끊김:** 저장 완료된 선택은 유지된다. 재접속 후 SSE의 빠진 이벤트와 현재 상태를 확인한다.
- **사용자 취소:** 취소 요청을 보낸 뒤 실제 job 상태를 표시한다. 이미 시작한 외부 모델 요청의 종료를 보장하지 못해도 늦은 결과는 적용하지 않는다.
- **앱 재시작:** 실행 중이거나 대기 중이던 job은 모두 `failed / INTERRUPTED`로 표시한다. 사용자 선택과 완료 단계는 남으며 명시적으로 재시도한다.
- **다른 창에서 변경:** 오래된 expected_revision으로 쓰기를 시도하면 충돌을 표시한다. 사용자 편집을 보존하고 최신 내용과 비교한 뒤 다시 적용한다.
- **세션 만료:** UI-10에서 새 로컬 토큰으로 접속한다. 작업 내용은 삭제되지 않으며 원래 작업의 최신 상태로 돌아간다.

## UJ-07 - 내보낸 뒤 승인 철회/작업 삭제

저장 기준이나 이번 자료의 허용을 철회하면 영향받은 현재 결과를 무효화한다. 앱의 과거 다운로드 URL을 직접 호출해도 현재 유효성 검사를 통과하지 못하면 받을 수 없다. 이미 사용자가 받은 파일은 회수하지 못한다.

작업을 삭제할 때는 대상 작업 이름과 삭제 범위를 보여주고 `DELETE` 입력 및 저장 기준 보존 확인을 받는다. 서버가 원자료/생성물/trace/event를 삭제하고 현재 job 결과가 다시 저장되지 못하게 한다. 원문을 담지 않는 별도 재사용 기준은 남는다. 사용자가 그 기준도 없애고 싶다면 기준 관리에서 철회한다. UI는 남는 기준과 삭제되는 내용을 혼동시키지 않는다.

## 2. 첫 시연에서 보여줄 순서

1. 일반 자료 사례에서 목적 입력->A/B/D 선택->같은 선택의 결과 연결을 먼저 보여준다.
2. B2B 사례에서 재현 환경이 없어도 문의가 완성되고 모르는 사실이 유지되는 것을 보여준다.
3. OSS 사례에서 준비된 확장으로 새 입력의 지정 오류와 수정 결과를 실제 실행한다.
4. 공개 수준을 낮추면 본문/표/첨부 전체가 바뀌고 이전 파일을 사용할 수 없음을 보여준다.
5. 새 자료에서는 저장한 기준을 재사용하되 새 방향을 계산하고, 수신자가 바뀌면 다시 묻는 것을 보여준다.

시연 순서와 기능 우선순위는 다르다. 실제 구현 순서는 [plan.md](plan.md)를 따른다. 고정 응답 시연/실제 모델 실행/녹화는 각각 표시하고, 보여주지 않은 실행을 성공으로 주장하지 않는다.
