# 가상 ParcelRelay 배송 이벤트 웹훅 문의

회사/제품/고객/ID/로그는 모두 시연용 가상 정보다. ParcelRelay-Demo는 실제 공급사나 서비스가 아니다. 아래 로그는 실제 요청 없이 구성한 합성 관찰 기록이다.

## 상황과 영향

가상 온라인 판매 서비스가 ParcelRelay-Demo Enterprise API v3의 배송 상태 웹훅을 받는다. 수신 애플리케이션 2026.10.27, Python 3.12, 리버스 프록시 뒤의 HTTPS 엔드포인트를 사용한다. 가상 테넌트 tenant_demo_42, 리전 demo-apne2다.

첫 배송 시도에서 수신 앱은 이벤트를 큐에 기록하고 204 응답을 기록했다. 프록시는 같은 요청에 대해 upstream timeout과 504를 기록했다. 따라서 공급사가 성공 응답을 받았는지는 모른다. 이후 동일 event_id가 다시 왔으며 delivery_id는 달랐다. 멱등성 처리가 없어 내부 알림 두 건이 생성됐다는 합성 업무 기록이 있다. 공급사 재시도 정책에 따른 정상 중복 전달인지 결함인지는 모른다.

다른 이벤트는 배송 중 상태 뒤에 배송 완료를 받았으나 늦게 도착한 배송 중 이벤트로 화면 상태가 되돌아갔다. 수신 순서와 occurred_at 순서가 달랐다. 순서 보장 범위나 권장 상태 병합 규칙은 확인하지 못했다. 서명 검증은 두 사례 모두 성공으로 기록됐으며 이것만으로 전달 순서가 보장되는 것은 아니다.

## 공급사에 물을 내용

지정 공급사에 event_id/delivery_id를 공개해 첫 요청의 응답 관찰과 재시도 이유를 확인하고 싶다. 재시도 조건/백오프/최대 보관 기간, 중복 제거 키의 범위와 권장 보관 기간, 이벤트 순서 보장 여부와 권장 병합 방법도 묻고 싶다. 공급사 콘솔과 내부 전달 trace에는 접근 권한이 없다. 공급사 측 원인을 확정하거나 외부 테스트 요청을 보낸 적은 없다.

## 공개 판단이 필요한 정보

추적 ID/테넌트/리전/정확한 시각은 공급사 조사에 필요한 범위를 각각 결정해야 한다. 관찰량.csv의 count는 관찰 시점별 분당 수신량이며 실패율이 아니다. 수신량 증가가 중복 전달을 일으켰다는 근거는 없다.

내부 전용: 가상 고객 DEMO_CUSTOMER_H, 가상 주문번호 ORDER-DEMO-8841, 고객 알림 문구와 할인 계약, https://orders.example.invalid/private/hooks/parcel, 내부 주소 10.23.8.14. 가상 인증 표식 DEMO_ONLY_SECRET_H는 무효 문자열이다. 공급사 조사에 원본 payload나 인증 헤더 전체가 필요한지는 확인하지 않았다.
